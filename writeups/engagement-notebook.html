The engagement notebook

Memory is worthless. That is not a metaphor — it is a measured fact about how recon goes wrong. Two weeks into an engagement you will "remember" seeing a v2 endpoint somewhere, in some bundle, maybe behind a flag you half recall. That memory is unsearchable, undated, and unverifiable. A dated note is evidence. Here is how I keep mine.

Scope first. Everything below assumes written authorization for the target. No scope, no recon — and no notes to take, because there is nothing to test.

1. One folder per engagement, same skeleton

Every engagement starts with the same directory layout, created before the first request. Consistency means I can navigate an old engagement years later without thinking:

$ mkdir -p engagement-name/{notes,evidence,bundles}
$ touch engagement-name/notes/log.md \
        engagement-name/notes/endpoints.md \
        engagement-name/notes/dead-ends.md
$ ls engagement-name/notes
dead-ends.md  endpoints.md  log.md

log.md is the daily journal. endpoints.md is the running inventory. dead-ends.md is the graveyard — and the graveyard matters more than it sounds.

2. The daily log: date, command, observation

Every entry in log.md starts with a date header and follows one discipline: write the observation the same day, or it did not happen. A typical entry looks like this:

## 2026-10-05

- crt.sh enum: 34 unique subdomains, 12 resolve (notes: subdomains.txt).
- /api/auth/prelogin returns salt + keyVersion before login form
  even renders. No auth required. Response:
  {"salt":"...","keyVersion":3}
- login POST transforms password client-side — check bundles for
  the submit handler next session.
- NOTE: host on 198.18.0.0/24 lab range responding slowly (~4s).
  Flag for later, don't hammer.

Notice what is not here: conclusions, hypotheses, excitement. The log records what I did and what came back. Interpretation is a separate pass, written later with the entries in front of me. Separating observation from interpretation is what makes the log trustworthy.

3. The endpoint inventory

endpoints.md is a living table — every endpoint the client exposes, whether I found it in a bundle, a sitemap, or a redirect chain. Columns stay simple:

$ cat engagement-name/notes/endpoints.md
| Endpoint                  | Method | Auth | Notes                    |
|---------------------------|--------|------|--------------------------|
| /api/auth/prelogin        | POST   | no   | returns salt, keyVersion |
| /api/auth/login           | POST   | no   | client-side password xform|
| /api/user/profile         | GET    | yes  | tested, 401 unauth OK    |
| /api/v2/session/refresh   | POST   | yes  | v1 deprecated? compare   |

This table is the attack surface in one glance. When I am stuck on a flow, I re-read it — the answer to "what haven't I looked at" is always in this file. I update it every session, even when nothing changed; the timestamp of the last update tells me how fresh the map is.

4. The dead-end log

This is the file most people skip, and the one that saves the most time. Every hypothesis that did not pan out goes into dead-ends.md with the date and the evidence:

## 2026-10-05

- /api/v1/export: identical 403 for valid session, expired session,
  and garbage token. Not an access-control difference — the endpoint
  is gated uniformly. Stop here.
- Suspected second OAuth client_id in chunk-9f2a.js: turned out to be
  a hardcoded test constant, never sent to the server. grep showed
  zero references outside the dead code path.

Why write down failures? Because your brain does not mark threads as closed. Without this file you will re-test the same dead endpoint three sessions later, burning an hour to rediscover what you already knew. A dead end written down stays dead — and sometimes a dead end from March becomes a live thread in June when the code changes, which is exactly why the date matters.

5. The notebook is greppable

Plain text notes across engagements compound. I keep all engagement folders under one directory, which turns past work into a searchable corpus:

$ grep -ri "prelogin" ~/engagements/*/notes/log.md | head
$ grep -ri "double-sha256\|AES-ECB" ~/engagements/*/notes/*.md

When a new target shows a familiar pattern — a salt returned before login, a crypto primitive in a bundle — I check how I approached it last time instead of starting from scratch. The notebook becomes a personal playbook written by my past self.

The rule

Commands produce output. Responses produce observations. Observations produce notes, the same day, with a date on them. Two weeks later, "I remember seeing something about a v2 endpoint" is worthless. A dated note is evidence — it is searchable, verifiable, and honest about what you actually knew and when.

The notebook is the least glamorous tool I own. It is also the one that compounds the fastest.
