ESP32 ADC2 goes blind when WiFi starts

Here is a bug that looks like broken hardware: a joystick axis reads perfectly on the bench, you add WiFi.begin() to the sketch, and the readings collapse to zero — or to 4095 — and never come back. The wiring did not change. The sensor did not change. The only change is that WiFi is now running. That is not a coincidence, and it is not a defective board. It is the ESP32's ADC2 unit being claimed by the WiFi driver.

Scope first. Everything here assumes written authorization for the target. No scope, no recon.

Two ADC units, one shared with WiFi

The classic ESP32 has two analog-to-digital converter units, and the pins are split between them in a way that is easy to miss on a pinout diagram:

  • ADC1 — 8 channels, GPIO 32, 33, 34, 35, 36, 37, 38, 39. Always available to your code.
  • ADC2 — 10 channels, GPIO 0, 2, 4, 12, 13, 14, 15, 25, 26, 27. Shared with the WiFi driver.

When WiFi starts, the driver takes over ADC2 for its own internal calibration work. From that moment on, analogRead() on any ADC2 pin returns garbage — typically a stuck 0 or a stuck 4095 — regardless of the actual voltage on the pin. Before WiFi starts, the same pin reads fine, which is exactly why this bug is so confusing: the code worked five minutes ago.

This is documented behavior, not a workaround for a broken chip. It applies to the original ESP32. (The ESP32-S2 and later parts handle ADC2 differently, so check the datasheet for your exact chip — but if you are on a classic ESP32, the rule below holds.)

Reproduce it in two minutes

The fastest way to convince yourself is a sketch that reads one ADC2 pin — GPIO 25, say — before and after WiFi connects, and prints both values:

#include <WiFi.h>

void setup() {
  Serial.begin(115200);
  Serial.print("Before WiFi: ");
  Serial.println(analogRead(25));
  WiFi.begin("ssid", "password");
  delay(2000);
  Serial.print("After WiFi:  ");
  Serial.println(analogRead(25));
}

void loop() {}

Compile and upload it with the Arduino CLI, then watch the serial output:

$ arduino-cli compile --fqbn esp32:esp32:esp32 adc2-demo
$ arduino-cli upload -p /dev/ttyUSB0 --fqbn esp32:esp32:esp32 adc2-demo
$ arduino-cli monitor -p /dev/ttyUSB0 -c baudrate=115200
Before WiFi: 1873
After WiFi:  0

The first reading is a real analog value. The second is the WiFi driver telling you, in effect, that the pin is no longer yours. If you see this exact pattern — good readings, then a stuck value the moment WiFi comes up — stop debugging the sensor. The sensor is innocent.

The fix: move to ADC1

The fix is a wiring change, not a code change. Move every analog input to an ADC1 pin: GPIO 32 through 39. A joystick is the classic case — its two axes land on GPIO 34 and 35, both ADC1, and they keep reading correctly with WiFi running, a web server up, or anything else the radio is doing.

After rewiring, re-run the same test against the new pin. The before/after comparison is the whole verification: if the reading stays sane with WiFi connected, the move fixed it. If it is still stuck, you have a different problem — wiring, a floating pin, or a dead sensor — and the I2C-scanner instinct applies here too: verify the hardware layer before blaming the code.

One more ADC1 detail worth knowing: GPIO 34 to 39 are input-only pins. They have no internal pull-up or pull-down resistors, so a floating input on those pins will drift. That is a separate, normal analog behavior — tie the pin to a real signal and it reads fine.

What if ADC1 is full?

Eight ADC1 channels cover most small builds, but if you genuinely run out, you have three honest options. First, read the ADC2 sensor before WiFi starts and cache the value, if a one-time reading is enough. Second, stop WiFi, take the reading, and restart it — ugly, but it works for slow, occasional measurements. Third, add an external ADC such as an ADS1115 over I2C: it is a separate chip, the WiFi driver cannot touch it, and it gives you four more channels with better resolution than the ESP32's built-in ADC anyway. What does not work is hoping ADC2 will behave once WiFi is up. It will not.

The rule of thumb

When you lay out an ESP32 board that will ever use WiFi, treat GPIO 32–39 as your analog pins and everything else as digital until proven otherwise. Write it on the schematic, in the pinout comment at the top of the sketch, wherever future-you will see it before wiring a sensor to GPIO 25. The five minutes this rule costs up front are nothing next to the afternoon you will spend chasing a "broken" joystick that was never broken — it was just wired to the wrong half of the chip.
