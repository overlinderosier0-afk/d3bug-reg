Mapping OAuth flows from the browser

OAuth looks complicated in diagrams and simple in the browser. That gap is where misunderstandings hide. Before I ever touch an auth flow with curl, I map it: every endpoint, every redirect, every parameter, in order, exactly as the browser sees them. This post is that mapping process — nothing but the DevTools network tab, a terminal, and a notes file.

Scope first. Everything below assumes written authorization for the target. No scope, no recon — that rule is non-negotiable in my workflow.

1. Start from the entry point

Most flows begin with one click — "Sign in with X". Open DevTools, switch to the Network tab, enable Preserve log, and click the button. Then write down, immediately: the full URL of the authorize endpoint, the client_id, the redirect_uri, the response_type, the scope, and the state. These are public, observable values — the browser sends them in cleartext on every single login.

2. Find the flow in the bundles first

I usually spot the flow before clicking anything. With the JavaScript bundles already downloaded locally, I grep for the flow's vocabulary:

grep -rhoE '"https?://[^"]*authorize[^"]*"' *.js | sort -u
grep -roiE '(redirect_uri|client_id|response_type|code_verifier|grant_type)[^"]{0,40}' *.js | sort -u

If the bundle defines the endpoints, the network tab later confirms them. Two independent sources describing one flow — and any mismatch between them is the most interesting thing I can find at this stage.

3. Walk the redirect chain, one hop at a time

The browser follows redirects automatically, which hides the interesting part: each hop carries parameters. To see them individually, replay the authorize request with curl and stop at the first redirect:

curl -s -D - -o /dev/null --max-redirs 0 \
  "https://auth.example.com/authorize?client_id=abc&redirect_uri=https%3A%2F%2Fapp.example.com%2Fcb&response_type=code&scope=openid+profile&state=xyz"

The Location header is the next hop. Read it. Note its parameters. Follow it manually the same way. A typical flow is three to six hops; at this pace, each one takes seconds to inspect and costs the server nothing a real user wouldn't.

4. Note the code exchange, don't replay it

Eventually a hop delivers a code to the redirect_uri — something like app.example.com/cb?code=...&state=.... The application then exchanges that code server-side for tokens (grant_type=authorization_code). I find the token endpoint in the bundles with a grant_type grep and note it in the map. I do not replay the exchange myself against a live server: mapping means knowing this step exists and where it happens, not interacting with it.

5. Inventory where the tokens land

After the exchange, the app holds tokens. My job is to inventory where they live, because the storage location determines everything about their exposure. Back to DevTools, Application tab: check localStorage, sessionStorage, cookies. For in-memory tokens, watch the network tab for Authorization headers on subsequent requests. Document what I find factually — "access token in localStorage under key X" is a design fact, not an attack.

6. Observe, don't interact

Everything above is observation. I click the same buttons a normal user clicks, I read what the browser already received, I replay GET requests the browser already made. No fuzzing the token endpoint, no replaying codes, no mutating parameters against a live server. If a hop returns something unexpected, it goes into the notes as a timestamped observation — not as a finding. Deciding what it means is a later step, on authorized scope, with a written plan.

7. The map itself

By the end I hold a dated document: the endpoint inventory in order, every parameter seen on each hop, the token storage locations, and the explicit list of things I chose not to touch. That map is what makes any later authorized testing precise instead of random — and it is exactly the kind of document a disclosure report needs when one of those steps turns out to matter.

Disclosure note. Techniques described here are methodology only. Specific findings from live engagements are reported privately to the vendor first and published here only after remediation or explicit permission.
