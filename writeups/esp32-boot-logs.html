Reading ESP32 boot logs: rst codes and invalid headers

The ROM bootloader talks before your firmware does. Every ESP32 prints its boot sequence on the serial console at power-on, and that block of text is the fastest diagnostic you have. It tells you why the board reset, what it found (or failed to find) in flash, and exactly where the flash layout disagrees with what you think you wrote. Here is how to read it.

Scope first. Everything here assumes written authorization for the target. No scope, no recon.

1. Open the console at 115200 baud

The boot ROM always speaks at 115200 baud. Find your port and attach before powering the board — the log starts the instant it resets:

$ ls /dev/ttyUSB* /dev/ttyACM*
/dev/ttyUSB0
$ screen /dev/ttyUSB0 115200

If the output is garbled characters instead of readable lines, you are almost certainly at the wrong baud rate. The ESP32 boot ROM uses 115200; your firmware may switch to something else later, but the first lines are always 115200. Save the session output to a file — boot logs scroll past fast and you will want to re-read them.

2. Anatomy of a normal boot

A healthy boot looks like this:

rst:0x1 (POWERON),boot:0x13 (SPI_FAST_FLASH_BOOT)
configsip: 0, SPIWP:0xee
clk_drv:0x00,q_drv:0x00,d_drv:0x00,cs0_drv:0x00,hd_drv:0x00,wp_drv:0x00
mode:DIO, clock div:1
load:0x3fff0030,len:4832
load:0x40078000,len:16460
load:0x40080400,len:4
entry 0x400805e4

The load: lines are the second-stage bootloader copying firmware segments into RAM; entry is the address it jumps to. If your log stops before entry, the problem is in the image itself. If it stops after it, your firmware is the problem.

3. The rst: code — why did it reset?

The first token, rst:0x1, is the reset reason register. These are the ones I look up most:

0x01  POWERON_RESET         - power applied, normal
0x03  SW_RESET              - software reset (esp_restart)
0x05  DEEPSLEEP_RESET       - woke from deep sleep
0x07  TG0WDT_SYS_RESET      - timer group watchdog fired
0x09  RTCWDT_SYS_RESET      - RTC watchdog fired
0x0C  SW_CPU_RESET          - CPU reset from software
0x0F  RTCWDT_BROWN_OUT_RESET - brownout: voltage dipped

A loop of 0x07 or 0x09 resets means the watchdog is killing your firmware before it finishes its first task — check blocking loops and long busy-waits. A loop of 0x0F brownouts during motor or servo movement is a power supply problem, not a code problem.

4. "invalid header: 0x..." — the most useful failure

This line appears when the ROM bootloader cannot find a valid image where it expects one:

invalid header: 0xffffffff

It is worth unpacking, because it names the actual bytes at the flash address the bootloader read. The ROM expects the second-stage bootloader at flash offset 0x1000, and the first byte of that image must be the magic byte 0xe9. So:

  • 0xffffffff means the bytes at 0x1000 are all erased flash. The most common cause: you flashed the application binary at the wrong address, so nothing landed where the bootloader lives.
  • An application image has magic 0xe9 too — but it belongs at 0x10000, not at 0x1000. Flash an app binary at offset zero and the ROM reads garbage where it expects its bootloader.

Verify the suspicion without guessing — read the header back and look at the first byte:

$ esptool.py --chip esp32 --port /dev/ttyUSB0 read_flash 0x1000 4 hdr.bin
$ xxd hdr.bin
00000000: e900 0000                             ....

First byte e9 at 0x1000: bootloader is present. All ff: erased flash, reflash the full image set. The standard ESP32 flash layout is: bootloader at 0x1000, partition table at 0x8000, boot_app0 at 0xe000, and the application at 0x10000. Writing the app image at 0x0 guarantees an invalid header — the single most common "board is dead" mistake I have seen.

5. "waiting for download" — the ROM gave up on flash entirely

Sometimes the log ends with the chip sitting idle instead of looping on invalid header. This means the ROM entered download mode: it is waiting for a new firmware upload. That happens when the EN/RESET line is held low together with the BOOT strapping pin pulled low, or when the board was designed to enter download mode on failed boot. If you see this and you did not ask for it, check your reset circuitry and the BOOT button before suspecting the firmware.

6. Capture every session

Boot logs are ephemeral — reset the board and they are gone. My bring-up routine: console attached and logged to a dated file before the first power-on, wrong baud rates fixed immediately, and the rst: code and any invalid header value written into the dated notes with the exact flash command that produced them. A dead board and a saved boot log is a ten-minute problem; a dead board and no log is an afternoon.
