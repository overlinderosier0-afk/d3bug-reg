Detecting anti-bot layers

Most of my testing time is spent on applications that decide, before I even see a login form, whether I am a human. Anti-bot layers sit in front of real endpoints and change everything about what your probes return. If you do not map them first, you will misread every response that follows. This post is about detecting these layers — figuring out which endpoints are gated, from the outside, without touching the gate itself.

Scope first. Everything below assumes written authorization for the target. No scope, no recon — and detecting a gate never authorizes bypassing it.

1. The first hint is in the response you did not ask for

Hit an endpoint with plain curl, no browser headers, and read what comes back. A bot layer announces itself in patterns, not in single responses:

$ curl -s -o /dev/null -w "%{http_code} %{size_download}\n" \
  https://target.example.com/api/auth/login
200 48213

A 200 with a large body on an API endpoint that should return small JSON is suspicious. Dump the headers and look for the classics — a Set-Cookie on the very first response that your next request is expected to echo back, or a body that is HTML instead of JSON:

$ curl -s -i https://target.example.com/api/auth/login \
  | grep -iE '^(HTTP|set-cookie|content-type)'
HTTP/2 200
set-cookie: __gate_token=eyJhbGciOi...; Path=/; HttpOnly
content-type: text/html; charset=utf-8

Then run the same request with a full browser User-Agent versus the default curl one. If the two responses differ — a challenge page for curl, the real page for the browser — you just observed User-Agent-based gating:

$ UA="Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36"
$ curl -s -A "$UA" -o browser.html https://target.example.com/api/auth/login
$ curl -s -o curl.html https://target.example.com/api/auth/login
$ wc -c browser.html curl.html
  1243 browser.html
 48213 curl.html

2. Read the challenge, don't fight it

Challenge pages are just HTML. Save one and read it like any other page: the title, the inline JavaScript, the cookie it asks the client to set before retrying. Product-agnostic signs of a bot challenge include JavaScript that runs and posts back a token, and document.cookie writes that must be echoed on the next request.

The goal of this step is a map, not a bypass: which paths serve the challenge and which pass through cleanly. Automating challenge-solving is interaction the engagement did not authorize — on a bug bounty it will usually get your account, and sometimes your IP, banned. Observe and note.

3. Grep the bundles for sensor logic

The client-side bundles often ship the detection logic in the open. The same grep pass I use for endpoint extraction doubles as a sensor survey:

$ grep -rhoiE '(webdriver|navigator\.userAgent|canvas\.toDataURL|deviceMemory|plugins\.length)' *.js \
  | sort | uniq -c | sort -rn | head

These strings tell you what the client collects about its environment. That explains why headless curl behaves differently from a real browser — and it tells you which behaviors are being measured, which is all the information you need for an accurate map. You are reading the application's own description of its defenses.

4. Per-control error codes are a gating signal

Some endpoints return distinct error codes per control: a missing cookie produces one code, an invalid challenge token another, a rate-limited client a third. Catalog them the same way you would catalog any error oracle — one request per variation, response written down immediately:

$ curl -s https://target.example.com/api/auth/login -H "Content-Type: application/json" \
  -d '{"user":"probe","pass":"probe"}'
{"code":"ERR_GATE_COOKIE","msg":"session cookie required"}

Each distinct code is a layer of the gate naming itself. The catalog becomes the legend for your gate map: when a probe fails later, you can say which layer stopped it instead of guessing.

5. Build the gate map in your notes

Now combine everything into a simple table in the engagement notebook — one row per endpoint, one column per condition:

endpoint                 | plain curl | browser UA | cookie present
/api/auth/login          | challenge  | 200        | 200
/api/auth/prelogin       | 200        | 200        | 200
/api/universal/redirect  | 403        | 200        | 200

Why this matters: probing a gated endpoint with curl and reading a 403 as "dead end" is a misread. The gate is part of the context, not the answer. And when you write the report, the gate map is evidence — you document the defense's presence and behavior. A bypass attempt is a different activity with different authorization, and on most of my engagements it is explicitly out of scope.
