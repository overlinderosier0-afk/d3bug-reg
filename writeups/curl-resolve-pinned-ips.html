Pinning IPs with curl --resolve

Sometimes DNS is the thing standing between you and your target, and not for any interesting reason. A filtered resolver that refuses to answer, a captive portal hijacking every query, a local network where port 53 is simply dead. You already know the IP — you resolved it over HTTPS, or it sits in your engagement notes — but the rest of your toolchain keeps asking the broken resolver and failing. That is exactly what curl --resolve is for.

Scope first. Everything here assumes written authorization for the target. No scope, no recon.

The problem, in one command

Your system resolver is broken, so this fails:

$ curl -s https://target.example.com/ | head -5
curl: (6) Could not resolve host: target.example.com

The TLS config is fine, the network is fine, the server is fine. Only the name lookup is dead. Editing /etc/hosts "fixes" it, but it is a system-wide change you have to remember to undo, and it requires privileges. There is a cleaner option that stays inside your shell session.

--resolve: one-off DNS, pinned to a command

curl --resolve host:port:ip tells curl: for this request, map this hostname to this IP and do not ask any resolver. The syntax is exact — hostname, port, IP, colon-separated:

$ curl --resolve target.example.com:443:93.184.216.34 \
  https://target.example.com/

The port matters: the pin applies to connections on that port only. The hostname in the URL stays untouched, so the Host header and — critically — the TLS SNI still carry the real hostname. The server never knows you bypassed DNS, and certificate validation works exactly as it should.

Where does the IP come from?

From a resolution path you trust, kept separate from the broken one. My usual answer is DNS over HTTPS, as covered in my earlier post on DoH:

$ curl -s "https://cloudflare-dns.com/dns-query?name=target.example.com&type=A" \
  -H "accept: application/dns-json" | jq -r '.Answer[].data'
93.184.216.34

The pattern is two steps: resolve once over HTTPS, then pin the result for every subsequent request. I put both in the engagement notes, because the IP is an observation like any other — worth recording, worth re-verifying later.

Verify the pin with -v

Never trust that the pin did what you think it did. -v shows you the connection plan before the request goes out:

$ curl -v --resolve target.example.com:443:93.184.216.34 \
  https://target.example.com/ -o /dev/null -s

* Added target.example.com:443:93.184.216.34 to DNS cache
* Hostname was NOT found in DNS cache
*   Trying 93.184.216.34:443...
* Connected to target.example.com (93.184.216.34) port 443
* SSL connection using TLSv1.3 / TLS_AES_256_GCM_SHA384
* ALPN: server accepted h2

Two lines tell you the whole story. Added ... to DNS cache confirms your pin landed. Trying 93.184.216.34:443 confirms curl is connecting there — while the log line right after still shows the hostname, which means SNI and certificate validation are operating on the real name. If you see Connected to with a different IP than your pin, something else (a proxy, a redirect) is in the path and you want to know that before you draw conclusions from the responses.

One pattern, the whole toolchain

The real payoff is consistency: every command in your pipeline uses the same pinned resolution, so results are comparable across tools. A shell variable keeps it tidy:

$ IP=93.184.216.34
$ curl -s --resolve "target.example.com:443:$IP" https://target.example.com/ \
  | grep -oE 'src="[^"]+\.js[^"]*"' | sed 's/src="//;s/"//' > bundles.txt
$ curl -s --resolve "target.example.com:443:$IP" https://target.example.com/api/prelogin \
  -H "Content-Type: application/json" -d '{}'

Different endpoints, different purposes, one pinned identity for the target. That matters for the comparison work: when I diff an unauthenticated response against an authenticated one, I need to know the only variable was the request itself — not a resolver flip-flopping between IPs mid-session.

What --resolve does not do

Honest limits, because they bite:

  1. It does not affect anything except curl. Your browser, other tools, and other processes still use the broken resolver. This is per-invocation, by design.
  2. It pins your chosen IP. If the IP you pinned is stale or wrong, every request confidently fails. Re-verify the address if responses suddenly change.
  3. It hides DNS-level behavior. If the target uses DNS-based load balancing or geo-routing, pinning one IP means you are only ever testing one edge. Note that in your notes — it is part of your scope picture.
  4. It lives and dies with the process. Nothing is written to disk, which is the point, but it also means each new shell session needs the pin again. Fine — that is what the engagement notes are for.

The takeaway

Broken DNS is an infrastructure annoyance, not a finding, and it should never slow down an engagement. Resolve once over a trusted path, pin the result with --resolve, verify with -v, and keep the IP in your dated notes. Your requests stay comparable, your toolchain stays honest, and the resolver can stay broken all week for all you care.
