Reading minified JavaScript like prose

A minified bundle looks hostile: one line, thousands of columns, variable names like e, t, n. But minification only removes whitespace and renames locals. The logic, the strings, and the API surface are all still there. You just need to read the file in the right order: format first, strings second, code paths third.

Scope first. Everything below assumes written authorization for the target. No scope, no recon — that rule is non-negotiable in my workflow.

1. Pretty-print before you read anything

Never read a bundle raw. Open it in the browser DevTools Sources panel and hit the pretty-print button ({}) — it re-indents the whole file instantly. If you are working from a local copy, most editors will do the same on paste. The variable names stay ugly, but structure is what you need first: you go from one unreadable line to functions, blocks, and nesting you can actually scan.

Save the downloaded bundles in the engagement folder next to your notes. I keep the collection step exactly as in my recon flow, so the files are already on disk:

curl -s https://target.example.com/ \
  | grep -oE 'src="[^"]+\.js[^"]*"' \
  | sed 's/src="//;s/"//' | sort -u

2. Read the strings, not the code

String literals survive minification untouched. Endpoint paths, query parameter names, error messages, header names — all of it is still plaintext. So the first pass is never "read the code". It is: dump every interesting string and build the vocabulary of the application.

grep -rhoE '"/api/[^"]+"' main.js | sort -u
grep -rhoE '"/[a-z0-9/_-]+\.php[^"]*"' main.js | sort -u
grep -roiE '"(redirect_uri|client_id|grant_type|prelogin|challenge)[^"]{0,40}' main.js | sort -u

Error strings are especially valuable. A message like "invalid session tag" or "prelogin required" tells you what the server checks and in what order — you get the auth state machine for free, before reading a single line of actual logic.

3. Identify the framework chunks by filename

Modern builds split into chunks, and the filenames tell you which chunk does what. This is where most people waste time: they grep the 2 MB vendor chunk instead of the 40 KB app chunk. Typical patterns:

# webpack / Vue CLI
js/chunk-vendors.[hash].js      # third-party libraries — skip first
js/app.[hash].js                # application code — read this
# Create React App
static/js/main.[hash].chunk.js  # application code
static/js/2.[hash].chunk.js     # vendor chunk
# Vite
assets/index-[hash].js          # usually the whole app bundle

Rule of thumb: the biggest file is almost never the interesting one. Start with the app chunk, and only open the vendor chunk when a call disappears into library code you need to understand.

4. Follow the event listeners, not the functions

Minified code has thousands of anonymous functions; the event listeners are the table of contents. In DevTools, the Elements panel shows every listener attached to a node, and clicking one jumps straight to the handler in the Sources panel. On a login page, that means: find the submit button, open its click listener, and you are standing at the start of the auth flow.

From there, trace backward and forward the same way every time:

  1. What values does the handler read from the form? (password, username, hidden fields.)
  2. What transforms are applied — hashing, encoding, concatenation — before the request?
  3. Which endpoint gets called, with which parameters, in which order?
  4. Where does each response value go: storage, memory, redirect URL?

Crypto primitives are easy to spot even minified: CryptoJS, AES, SHA256, MD5, createHash. Map the sequence — input, transforms, output — because the sequence is what matters, not any single mangled function name.

5. Search before you scroll

Scrolling a 10,000-line pretty-printed file is how you lose an afternoon. Search instead. Start from a string you found in step 2, find where it is used, then read only that function. A few searches that almost always land:

# where is this endpoint actually called?
grep -n "api/auth/prelogin" main.js
# where does the token end up?
grep -n -iE "localStorage|sessionStorage|setItem|document.cookie" main.js
# what redirects happen?
grep -n -iE "location\.href|window\.open|redirect" main.js | head -30

Each hit is a waypoint. Read the 20 lines around it, note what you learned, and follow the next thread. You are never "reading the bundle" — you are walking a graph, one edge at a time.

6. Keep the map as you go

Minified code punishes re-reading: the function you understood at 2 PM is incomprehensible again at 4 PM. So write it down immediately — endpoint, purpose, inputs, outputs, one line each, dated. This is the same engagement notebook discipline I use everywhere else: memory is worthless, a dated note is evidence. Two weeks later, "the prelogin thing returns a salt" beats re-tracing the whole call chain.

What this gives you

After this process, the bundle stops being a wall of noise and becomes a specification: every endpoint the client knows, every auth step in order, every storage location for tokens. Most of the interesting threads I have ever pulled started as a single odd string literal that only looked odd because I had mapped everything around it first.
