Tracing client-side crypto in minified bundles

Login forms almost never send your password as-is. Hashing, salting, encryption, token assembly — modern frontends transform credentials in the browser before anything hits the wire. That logic is shipped to every visitor in the JavaScript bundle, which makes it public documentation of how auth works. Here is how I read it, step by step, without source maps.

Scope first. Everything below assumes written authorization for the target. No scope, no recon — that rule is non-negotiable in my workflow.

1. Get the bundles and pretty-print them

Never read minified code in the browser debugger if you can avoid it. Download the bundles, keep a pristine copy, and work on formatted copies:

mkdir -p bundles && cd bundles
curl -s https://target.example.com/login | grep -oE 'src="[^"]+\.js' ...
# (bundle extraction as covered in the recon write-up)
npx prettier --write '*.js'        # or: js-beautify, the point is readability

Minified identifiers like a, t, e stay ugly, but string literals never lie. That is where the hunt starts.

2. Hunt the primitives first

Before opening a single file, search for crypto vocabulary across everything. The hits cluster around the functions that matter:

grep -rhoE '(CryptoJS|crypto-js)' *.js | sort -u
grep -rhoE '(AES|SHA256|SHA-256|SHA512|MD5|Hmac|PBKDF2)' *.js | sort -u
grep -rhoiE '(createHash|createHmac|subtle\.digest|getRandomValues)' *.js | sort -u
grep -rhoE '"(mode|padding|iv|salt)[^"]{0,30}' *.js | sort -u

Each hit gives you a file and a neighborhood. CryptoJS.AES.encrypt in chunk-vendors.js is the library itself — boring. The same string one file over, next to /api/login, is the application code calling it. Follow the callers, not the library.

3. Find the submit handler

Anchor on the login form. Search for password next to event wiring — addEventListener, onClick, onSubmit, .submit. You are looking for the function that reads the password field, because everything downstream of it is the transform chain:

grep -rn 'password' login.js | grep -iE '(listener|submit|click|form)' | head -20

Once you have the handler, read it line by line. It usually does three things: validate, transform, send. The middle part is your target.

4. Walk the chain backward from the network call

Find the fetch/axios/xhr that posts to the login endpoint, then trace each parameter backward to its origin. A typical chain reads like this in pseudocode:

h1 = sha256(password)            # first transform
h2 = sha256(h1 + salt)           # salt arrives from an earlier prelogin call
payload = aesEncrypt(h2, key)    # final value sent as the password parameter

This is a generic illustration, not any real target's logic. What you are after in real code is the same skeleton: inputs (password, salts, timestamps, nonces), transforms in order, and the final value that goes on the wire. Salt values often come from a /prelogin-style endpoint — check the network tab to confirm which response feeds the code.

5. Confirm on the wire

Code reading is a hypothesis; the network tab is the test. Type a known password into the login form, capture the outgoing request, and check that the parameters match what your reading predicted. If the code says the client hashes twice and the request body carries a 64-hex-char value, your map is right.

One request at a time, human pace. You are observing the app's normal behavior, not hammering anything.

6. Write down the map

Record the chain exactly: endpoint sequence, parameter names, transform order, where salts and keys come from, where the session value lands afterward (memory, storage, redirect URL). This map becomes the reference for everything later — reproducing steps in a disclosure report, understanding a session flow, or simply not re-reading the same bundle twice.

What this gives you

A precise understanding of the auth design as the client implements it — which the vendor's docs may not describe. That understanding is what turns a vague "something odd in the login flow" into a clear, reproducible report the vendor can act on. The bundle told you everything; you just had to read it like prose.

Disclosure note. Techniques described here are methodology only. Specific findings from live engagements are reported privately to the vendor first and published here only after remediation or explicit permission.
