Sensor silent? Scan the I2C bus first

Every silent peripheral ends in the same place: you, staring at code that probably does not contain the bug. The OLED stays black, the sensor returns nothing, and the instinct is to rewrite the driver, swap the library, or re-read the wiring diagram for the fifth time. Don't. The cheapest experiment on the bench takes five minutes and answers the only question that matters first: is anything even on the bus?

Scope first. This covers your own hardware and hardware you have permission to work on. No scope, no probing — that rule applies to benches, not just networks.

1. The scanner sketch

On the ESP32, the default I2C pins are GPIO21 for SDA and GPIO22 for SCL — a bare Wire.begin() uses them. The scanner probes every address from 1 to 126 and reports which ones acknowledge. It is the same sketch the Arduino community has passed around for a decade, because it works:

#include <Wire.h>

void setup() {
  Serial.begin(115200);
  Wire.begin();  // SDA=GPIO21, SCL=GPIO22 on ESP32
  Serial.println("Scanning I2C bus...");
}

void loop() {
  int found = 0;
  for (uint8_t addr = 1; addr < 127; addr++) {
    Wire.beginTransmission(addr);
    if (Wire.endTransmission() == 0) {
      Serial.print("Found device at 0x");
      Serial.println(addr, HEX);
      found++;
    }
  }
  Serial.print(found);
  Serial.println(" device(s) found.");
  delay(5000);
}

Flash it, open the serial monitor at 115200 baud, and read the output. There are two possible outcomes, and both are answers.

2. An address appears — the address is the contract

If the scanner reports a device, write the address down and compare it with what your library expects. The usual suspects on a bench:

SSD1306 OLED        0x3C or 0x3D   (SA0 pin / solder pad selects)
MPU6050 / DS3231    0x68
BMP280 / BME280     0x76 or 0x77
PCF8574 LCD pack    0x27 or 0x3F

The classic trap is 0x3C vs 0x3D: two "identical" OLED boards, one solder pad different, two different addresses. The Adafruit SSD1306 constructor takes the address explicitly, so the fix is one constant — not the wiring, not the library:

#include <Adafruit_SSD1306.h>
#define SCREEN_WIDTH 128
#define SCREEN_HEIGHT 64
Adafruit_SSD1306 display(SCREEN_WIDTH, SCREEN_HEIGHT, &Wire, -1);

// in setup():
if (!display.begin(SSD1306_SWITCHCAPVCC, 0x3C)) {  // use the FOUND address
  Serial.println("SSD1306 allocation failed");
  for (;;);
}

If the scanner found 0x3D and the code passes 0x3C, begin() fails and the screen stays black. This is the single most common "dead OLED" cause I have seen, and it is never found by reading the driver source — only by asking the bus who is there.

3. No devices found — work the list, in order

An empty scan is not a dead end; it is a narrowing. Check in this order:

  1. Wrong pins. Wire.begin() with no arguments assumes GPIO21/GPIO22 on the ESP32. If you wired SDA and SCL to other pins, call Wire.begin(sdaPin, sclPin) explicitly — a swapped SDA/SCL pair answers to nothing.
  2. Power and ground. Is the module getting the voltage it expects (3.3V, or 5V if it is a 5V module)? And is its ground actually shared with the ESP32's ground? A module powered from a separate rail with a floating ground cannot answer anything.
  3. Pull-ups. I2C requires pull-up resistors on SDA and SCL. With one or two devices on short wires, the ESP32's internal pull-ups are usually enough, and most ready-made modules already include them. But some bare sensor boards do not — if the bus is flaky rather than dead, add external 4.7k resistors from SDA and SCL to 3.3V.
  4. Monitor baud. The scanner prints at 115200. A monitor left at 9600 shows garbage, which reads as silence. Match the baud before concluding anything.
  5. The module itself. Pins, power, common ground, pull-ups, and baud all verified, and the bus is still empty? The module is now the suspect — not the code.

Closing

The I2C scanner is not a tool of last resort; it is the first thing you run. It costs five minutes and splits the problem space in half: if something answers, the bug is in the address or the library call; if nothing answers, the bug is in the pins, the power, or the module. Only after the scan comes back clean — address confirmed, library fed the right constant — does the application code deserve any suspicion. Scan first, blame the code last.
