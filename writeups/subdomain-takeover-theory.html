Subdomain takeover: the theory

Some subdomains are promises that were never cancelled. A campaign page was spun up on a third-party host, the campaign ended, the account was closed — but the CNAME record stayed. That leftover pointer is a dangling DNS record, and the theory of subdomain takeover is the theory of those pointers.

This post covers how I check for them: DNS-only observation, a human-paced workflow, and a hard line I never cross. No exploitation, no account claims, no target names — the check itself is the whole topic.

Scope first. Everything below assumes written authorization for the target. No scope, no recon — that rule is non-negotiable in my workflow.

1. What "dangling" actually means

A DNS record is an instruction, not a guarantee. A CNAME says: "for this name, go look at that other name instead." It says nothing about who currently controls the destination. When a team stops using the destination — closes the account, deletes the project, lets the trial lapse — the instruction survives anyway. The pointer dangles.

The important mental shift: the vulnerability is not in DNS itself. It is in the gap between two facts that DNS lets you observe — this subdomain points at a third-party service and the organization no longer holds that service. The first fact is checkable with pure DNS queries. The second is something you verify carefully and document — never something you test by grabbing the resource yourself.

2. Build the subdomain list

Dangling records hide inside the ordinary subdomain list, so the check starts where all my recon starts — Certificate Transparency logs. Same command as always:

curl -s "https://crt.sh/?q=%25.example.com&output=json" \
  | jq -r '.[].name_value' \
  | sed 's/\*\.//g' | sort -u > subdomains.txt
wc -l subdomains.txt

This is a read-only query against a public log. It produces the seed list for everything that follows, and it goes into the engagement folder with today's date.

3. Ask DNS what each one points to

The entire check happens at the DNS layer. For each subdomain, the question is simple: does this name resolve to an A record the organization controls, or a CNAME pointing elsewhere? When the local resolver is untrustworthy, I query over HTTPS exactly the way I would for any other recon task:

curl -s "https://cloudflare-dns.com/dns-query?name=sub.example.com&type=CNAME" \
  -H "accept: application/dns-json" \
  | jq -r '.Answer[]? | "\(.name) -> \(.data)"'

Across the whole list, a small loop keeps the requests sequential and human-paced:

while read -r sub; do
  printf '%s : ' "$sub"
  curl -s "https://cloudflare-dns.com/dns-query?name=${sub}&type=CNAME" \
    -H "accept: application/dns-json" | jq -r '.Answer[]?.data // "no CNAME"'
done < subdomains.txt > cname-map.txt

Reading cname-map.txt is the core skill of this check. A CNAME to a name inside the organization's own zone is ordinary delegation. A CNAME pointing at an external hosting platform's hostname — the kind of target you see when a site was once deployed on a third-party service — is a candidate to document. Candidate is a deliberately weak word: a pointer to a third-party service is not a finding. It is a question waiting for authorization and careful verification.

4. Compare what the browser sees — passively

DNS tells you where the pointer goes; the rendered page tells you whether anyone is home. One request, read fully, nothing more:

curl -s -D - https://sub.example.com/ -o /tmp/sub-body.html | head -20

Then compare. If the page matches the organization's real content, the delegation is live and the thread ends here. If it matches a generic "nothing is hosted here" page from the platform, the candidate survives one more round of scrutiny — as a documented observation, not as a verdict. Identical versus different responses is the same comparison signal I use everywhere else; here it just has one specific question attached.

That single fetch is the limit of my interaction. I never create an account on the platform, never deploy content to the name, never complete a claim — claiming the resource would be acting on the target, which is beyond what a recon check is for, and usually beyond the written scope anyway.

5. The hard rules of this check

Theory is only useful if the discipline around it is real. Mine, for dangling records:

  1. DNS only decides. The CNAME chain is the evidence. Page content is context, not proof.
  2. Never claim. If a record dangles, the finding is reported to the vendor — the reporter's job ends at the report.
  3. One request at a time. Loops stay sequential. This check needs no concurrency and deserves none.
  4. Out of scope means stop. If the candidate sits outside the authorized scope, it goes into the notes as an observation, not a probe.

6. What goes in the notebook

A dangling-record observation that is not written down might as well not exist. My entries follow a fixed format, same day, every time:

[2026-10-17] subdomain check — example.com
- sub: promo.example.com
- CNAME chain: promo.example.com -> legacy-campaign.hostingprovider.net
- resolver: DoH via cloudflare-dns.com
- page: generic provider "no site here" response (single passive GET)
- decision: candidate, in scope —> reported to vendor, no further action

That note is the deliverable. It contains the evidence, the method, and the explicit decision — everything a vendor needs to verify the observation independently, and everything that proves the check never crossed the line.
