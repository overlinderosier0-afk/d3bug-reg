When DNS lies: resolving over HTTPS

One of the most confusing failures in recon is also one of the simplest: the browser loads a page fine, but the terminal says curl: (6) Could not resolve host. Nothing is down. The network works. Your resolver is broken — or filtered. Fighting it is a waste of time; routing around it takes one command.

Scope first. Everything below assumes written authorization for the target. Resolving a hostname you are authorized to test is normal recon; doing it against systems you have no permission to touch is not.

How you notice the lie

The symptom is asymmetric: the browser (often in DoH mode, bypassing the system resolver entirely) reaches the host, while the terminal cannot. Confirm it is a resolver problem before anything else:

$ curl -sI https://target.example.com/ -o /dev/null -w "%{http_code}\n"
curl: (6) Could not resolve host: target.example.com
$ dig target.example.com +short
;; connection timed out; no servers could be reached

If dig times out while the browser works, your DNS path is the problem. Common causes on hostile networks: captive portals, ISP resolvers that filter, or outbound port 53 blocked entirely. The fix is not to argue with the router — it is to stop using port 53.

Resolve over HTTPS instead

DNS-over-HTTPS carries the query over a plain HTTPS request to a resolver you trust. Cloudflare's endpoint speaks the JSON API I reach for first:

$ curl -s "https://cloudflare-dns.com/dns-query?name=target.example.com&type=A" \
  -H "accept: application/dns-json" | jq -r '.Answer[].data'
93.184.216.34

Two things to remember about this command:

  1. The accept: application/dns-json header is mandatory — without it you get the binary DNS wire format, which curl will print as garbage.
  2. Port 443 is doing the work here. If HTTPS works at all on your network, this works, because it looks like any other web request.

You can resolve other record types the same way — type=AAAA, type=CNAME, type=TXT — by changing one parameter. For a quick sanity check of several subdomains, wrap it in a shell loop:

$ for h in a.target.example.com b.target.example.com; do
  echo -n "$h -> "
  curl -s "https://cloudflare-dns.com/dns-query?name=$h&type=A" \
    -H "accept: application/dns-json" | jq -r '.Answer[]?.data // "no answer"'
done
a.target.example.com -> 93.184.216.34
b.target.example.com -> no answer

The .Answer[]? with the optional operator matters: a non-existent name returns no Answer key at all, and without the ? jq exits non-zero mid-loop.

Pin the result with curl --resolve

Knowing the IP is only half the battle — every subsequent tool still consults the broken resolver. curl --resolve overrides DNS for one request, which is exactly what you want:

$ curl -sI https://target.example.com/ --resolve target.example.com:443:93.184.216.34 \
  -o /dev/null -w "%{http_code}\n"
200

This stays correct even on shared hosting and CDNs: --resolve only replaces the address lookup, so TLS SNI and the Host header still carry the original name. Verify the handshake with -v and confirm the TLS certificate belongs to the hostname you asked for, not the IP.

One catch: the pinned IP lives only in that one curl process. If you are chaining several probes, export the IP into a variable and reuse it:

$ IP=$(curl -s "https://cloudflare-dns.com/dns-query?name=target.example.com&type=A" \
  -H "accept: application/dns-json" | jq -r '.Answer[].data')
$ curl -sv https://target.example.com/api/prelogin \
  --resolve target.example.com:443:$IP | head -5

This pattern — resolve once over HTTPS, pin everywhere — unblocks the entire rest of your toolchain without touching a single system setting.

Why I don't just edit /etc/resolv.conf

Changing the system resolver feels permanent and is rarely possible: you may lack root on the box, the file may be managed by NetworkManager, and on hostile networks the new nameserver can be filtered exactly like the old one. The DoH route needs no privileges, no restart, and survives moving between networks — which is the whole point of a recon laptop.

What this gives you

DNS is the first dependency in every recon pipeline, and it fails silently — "could not resolve host" hides whether the target is dead or your network is lying. Resolving over HTTPS turns that ambiguity into a fact: you get the answer from a resolver you can see, then pin it so the rest of your commands stop depending on a network you can't trust. When the resolver works again, drop the pinning. Until then, this keeps the engagement moving.
