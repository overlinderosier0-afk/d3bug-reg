My recon toolkit: curl, jq, and patience

People expect a long list of exotic scanners. My actual toolkit fits in one line: curl, jq, grep, and the discipline to read every response. Nothing in this post is a vulnerability claim and nothing here is new — it is just the set of small commands that does most of the real work, plus the habit that makes them compound.

Scope first. Everything here assumes written authorization for the target. No scope, no recon.

curl: the whole request, on purpose

A browser hides half of what matters. With curl I build the request myself — headers, method, data — and I see exactly what comes back, headers included. This is how I probe one endpoint at a time, at a human pace:

$ curl -s -i https://target.example.com/api/v1/hotQuestions?frontendId=100 \
  -H "User-Agent: Mozilla/5.0" \
  -H "Accept: application/json"

HTTP/2 200
content-type: application/json
...response body...

The flags that pay off most: -s (silent, no progress meter), -i (show response headers — status, content type, rate-limit headers), -v (full handshake detail when something behaves oddly), and -o file to save bodies for later diffing. When the local resolver is broken or filtered, I pin the IP directly instead of fighting DNS:

$ curl -s https://target.example.com/api/health \
  --resolve target.example.com:443:203.0.113.10 \
  -w "\nHTTP %{http_code} in %{time_total}s\n"

The -w format prints the status code and timing on its own line — a cheap habit that makes every probe comparable.

jq: the JSON shovel

APIs return nested JSON and I want the interesting field, not the whole dump. jq turns a wall of braces into a one-line answer:

$ curl -s "https://target.example.com/api/v1/items?limit=50" \
  | jq -r '.data.items[] | [.id, .name, .status] | @tsv'

1234    Widget A    active
1235    Widget B    pending

Three patterns I use constantly: jq '.something.nested' to navigate, jq -r for raw output without quotes, and jq 'keys' to discover the shape of a response I've never seen before. Combined with grep and sort -u, a JSON endpoint becomes an inventory in one pipe.

grep: hunting endpoints in plain sight

Once bundles are saved locally, string search beats cleverness. Before I open any file, I pull the structure out with recursive patterns:

$ grep -rhoE '"/api/[^"]+"' js/ | sort -u | head -30
"/api/login"
"/api/prelogin"
"/api/universal/oauth"
...

$ grep -rhoE '"https?://[^"]+"' js/ | sort -u

The -o flag prints only the matching part, -r walks the directory, and sort -u deduplicates. Within a minute I have the endpoint list, the absolute URLs, and a pile of keywords — prelogin, grant, redirect_uri, client_id — each one a thread to pull. No source maps needed.

When DNS lies: resolve over HTTPS

Sometimes the local resolver answers garbage — filtered networks, captive portals, or a resolver that simply drops queries. Rather than debugging the network, I resolve over HTTPS and pin the result:

$ curl -s "https://cloudflare-dns.com/dns-query?name=target.example.com&type=A" \
  -H "accept: application/dns-json" \
  | jq -r '.Answer[].data'
203.0.113.10

One request, JSON back, no dependency on the system resolver. The returned IP feeds straight into curl --resolve, and the rest of the toolchain works exactly as usual. This two-step dance — DoH lookup, then pinned requests — is the most reusable trick in this whole post.

Patience: read every response

The toolkit is small because the method is slow on purpose. One request, one response, read fully. Compare the unauthenticated response with the authenticated one. Compare the valid parameter with the mutated one. Identical responses to different inputs usually mean a dead end; different responses mean a thread. No scanner makes this comparison — your eyes do, and they need a second per request.

This pace has a second benefit: on an authorized engagement it keeps the noise near zero. Nobody's logs look like an attack, because nothing I send is one.

Notes: the tool that isn't installed

The final piece is not a command. Every endpoint, every observed behavior, every dead end goes into dated notes the same day. My log entries look like this:

2026-09-27 10:15 — GET /api/v1/hotQuestions?frontendId=100
  200, 41 items, same body for 100/101/99 → likely a static config,
  not an access-control signal. Moving on.

Two weeks later, memory says "I think I saw something about a v2 endpoint." A dated note says whether you did. That difference is worth more than any tool.

Putting it together

That is the whole kit: curl to speak HTTP precisely, jq to carve JSON, grep to mine bundles, DoH plus --resolve to survive broken networks, and dated notes to keep it all. Master these and the expensive tooling becomes optional — the signal was never in the tools anyway. It is in reading what the application already tells you.
