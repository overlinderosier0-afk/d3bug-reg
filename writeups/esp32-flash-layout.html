ESP32 flash layout: where each binary goes

Every invalid header: 0x... error has a backstory. On ESP32, most of those backstories are really about one number: the flash offset where a binary was written. The ROM bootloader expects each piece of firmware at an exact address, and it does not negotiate. Put the app image at the wrong offset and the board either prints garbage or reboots in a loop — not because the firmware is broken, but because nothing is where the boot process goes looking for it. This is the map.

Scope first. This covers your own hardware and hardware you have permission to work on. No scope, no probing — that rule applies to benches, not just networks.

The four addresses that matter

A standard ESP-IDF-style flash image is four binaries at four fixed offsets:

0x1000   second-stage bootloader   (loaded by the ROM bootloader)
0x8000   partition table           (where every flash region is defined)
0xE000   boot_app0                 (wakeup + RF calibration stub)
0x10000  app firmware              (your program)

The boot sequence is mechanical: the ROM code burned into the chip loads the bootloader from 0x1000. The bootloader reads the partition table at 0x8000, finds the factory app region, and jumps to the app at 0x10000. Miss any step — corrupt header, missing partition entry, app at the wrong offset — and the chain stops right there, loudly.

Why flashing an app image at 0x0 fails

Release binaries are almost always app images: their first byte is the magic byte 0xE9. You can confirm this without booting anything:

$ xxd firmware.bin | head -1
00000000: e9d5 0a3c 4008 8d32 0000 0c00 0000 0000  ...<@..2........

If that file is written at offset 0x0, the ROM bootloader wakes up, checks address 0x0 for a bootloader image header, finds app image magic instead, and reports invalid header. The firmware is fine; the address was wrong. Offset 0x0 is never the right home for an app image — that space belongs to the bootloader's header format, not to 0xE9.

This is the single most common reason a freshly flashed board prints an error and does nothing else. Before suspecting the hardware, the wiring, or the USB adapter, check where you wrote the file.

Writing a complete image with esptool

When you have the four pieces, write them in one command so nothing is forgotten. Offsets first, filenames after — each pair is one write:

$ esptool.py --chip esp32 --port /dev/ttyUSB0 --baud 921600 \
    --before default_reset --after hard_reset write_flash -z \
    --flash_mode dio --flash_freq 40m --flash_size detect \
    0x1000 bootloader_dio_40m.bin \
    0x8000 partitions.bin \
    0xe000 boot_app0.bin \
    0x10000 firmware.bin

The flags worth remembering: --flash_size detect probes the actual chip instead of trusting a config file, and -z compresses the transfer so a full write takes seconds instead of minutes. If the board does not enter download mode automatically, hold BOOT while pressing EN once.

Start from a clean chip

Switching between firmware builds or partition schemes leaves stale data behind. When nothing adds up, erase everything and reflash from zero:

$ esptool.py --chip esp32 --port /dev/ttyUSB0 erase_flash

Erase is especially important when a previous flash had a different partition table: an old 0x8000 entry pointing at a region the new app does not fill will mislead the bootloader even if all four new binaries are written correctly.

Verify what you actually wrote

Do not trust the write log alone — read the region back and check the magic byte at the offset where the bootloader will look for it:

$ esptool.py --chip esp32 --port /dev/ttyUSB0 \
    read_flash 0x10000 0x100 app_head.bin
$ xxd app_head.bin | head -1
00000000: e9d5 0a3c 4008 8d32 0000 0c00 0000 0000  ...<@..2........

If the first byte at 0x10000 is 0xE9, the app landed where the bootloader expects it. If it is 0xFF, the write did not happen at that address. This two-minute read-back has saved me more debugging sessions than any oscilloscope.

The mental checklist

  1. App image (0xE9 at byte 0) always goes to 0x10000, never 0x0.
  2. Bootloader, partition table, and boot_app0 travel with the app — flash all four together.
  3. Changing partition schemes? erase_flash first, then write.
  4. When the board prints invalid header, verify the offset before touching anything else.

The ESP32 boot process is unforgiving but completely deterministic. Learn the four addresses and half of all flashing failures turn into a one-line fix.
