Why I test at a human pace

Most testing tooling is built for speed: hundreds of requests a second, wordlists sprayed at endpoints, dashboards full of green and red. I do the opposite. On an engagement I send one request at a time and read every response before sending the next. It is slower. It is also, in my experience, where the real findings come from.

Scope first. Everything below assumes written authorization for the target. No scope, no recon — that rule is non-negotiable in my workflow.

One request, one question

Every manual probe starts as a sentence in my notebook: "What happens when I request this endpoint without a session cookie?" Then exactly one request answers it:

$ curl -s -i https://target.example.com/api/v1/profile
HTTP/2 401
content-type: application/json

{"error":"missing_auth","code":1001}

One question, one answer. Then the next question follows from what I just learned: "What changes with a valid session?" Then: "What changes with a mutated parameter?" This is the whole technique — a chain of questions where each link is forged from the previous answer.

A scanner cannot do this. It fires questions it decided before seeing any answers. The response of request #4 almost always changes what request #5 should be — but the scanner already sent it.

Read the whole response

Reading a response means the headers and the body and the timing. Headers leak server software, cache behavior, and session handling decisions. Error bodies in JSON carry the per-failure codes that betray system layers (code:1001 vs code:1002 tells me two different checks ran). Timing tells me whether a code path did real work or bailed out early.

$ curl -s -o /dev/null -w "%{http_code} %{time_total}s %{size_download}b\n" \
  https://target.example.com/api/v1/profile
401 0.083s 38b

At a human pace, noticing that one variant took 800ms while the others took 80ms is easy — you were there when it happened. In a 10,000-row report, the same anomaly is a number in a column nobody sorts.

Compare, don't just collect

Responses are only meaningful against each other. My loop is: save the baseline, save the variant, diff them:

$ curl -s https://target.example.com/api/v1/profile > noauth.txt
$ curl -s -b session.txt https://target.example.com/api/v1/profile > auth.txt
$ curl -s -b session.txt "https://target.example.com/api/v1/profile?id=999" > mutated.txt
$ diff noauth.txt auth.txt; diff auth.txt mutated.txt

Identical responses to different inputs usually mean a dead end — stop pulling that thread. Different responses mean the application reacted to something I changed, and that something is now a question for the notebook. This comparison discipline is the entire probing loop: baseline, mutate, diff, note, repeat.

The noise argument

Speed has a cost that reports don't show. Automated traffic lights up WAFs, fills application logs with junk, trips rate limits, and — on a live system — risks degrading the service you were hired to protect. I have seen engagements where the first sign of trouble was a rate-limit banner that swallowed the very endpoints the tester wanted to study.

One manual request per few seconds is indistinguishable from a careful user. It stays far under throttling thresholds, it never floods logs, and it leaves a clean, readable trail if the client's security team ever asks what I did. "Here is every request, in order, with my notes" is a sentence a scanner user cannot say.

Slow is a forcing function for understanding

The hidden benefit: the pace forces me to actually understand the system. Between requests I am thinking — about the auth flow I traced in the bundles, about what that code:1002 implies, about what a sane developer would have written next. That thinking is the test; curl is just the instrument.

I am not romanticizing slowness. Some work genuinely benefits from automation: subdomain resolution, bulk bundle downloads, comparing two hundred endpoints for version differences. But the moment a request becomes a question about behavior, the tool changes back to one pair of eyes and one terminal.

What this gives you

High signal per request. Near-zero noise and risk. A notebook that reads like a narrative instead of a spreadsheet. And findings that arrive with context attached, because you watched them happen one question at a time.

Test at a human pace. The machines can wait.

Disclosure note. Techniques described here are methodology only. Specific findings from live engagements are reported privately to the vendor first and published here only after remediation or explicit permission.
