Harvesting endpoints from JavaScript bundles

Before I probe an application, I read what it already tells the browser. A modern front end ships its routing, its API calls, and much of its auth logic as JavaScript bundles. Collecting those bundles and grepping them gives me an endpoint inventory before I send a single request to an API path. This post covers collection and extraction only. A string in a bundle is a lead, not a finding, and no conclusion about any endpoint follows from this step alone.

Scope first. Everything below assumes written authorization for the target. No scope, no recon — that rule is non-negotiable in my workflow.

1. Collect the bundles served by the application

I start from a page the application serves in scope, fetch its HTML, and extract the script references. The filenames are usually hashed, which is useful: a hash tells me when a deploy has replaced a bundle and my copy is stale.

mkdir -p bundles
curl -s https://target.example.com/ \
  | grep -oE 'src="[^"]+\.js[^"]*"' \
  | sed 's/src="//;s/"//' | sort -u > bundles.txt
cat bundles.txt

Relative paths need the origin put back on; absolute URLs need a scope check first. I download only bundles served by a host that is in scope, and skip third-party scripts — analytics and widgets belong to someone else's scope and add noise without adding application routes.

while IFS= read -r bundle; do
  curl -s -o "bundles/$(basename "$bundle")" \
    "https://target.example.com$bundle"
done < bundles.txt
ls -l bundles/

Lazy-loaded chunks are the gap in this first pass: a bundle loaded only after a click or a login never appears in the first page's HTML. I re-collect after each in-scope page I visit, and keep every collection in its own dated folder so an old bundle never masquerades as the current build.

2. Grep for paths before reading any file

With the bundles on disk, I do not open them yet. I search for structure across all of them at once and write the results to files I can sort:

grep -rhoE '"/api/[^"]+"' bundles/*.js | sort -u > endpoints.txt
grep -rhoE "'/api/[^']+'" bundles/*.js | sort -u >> endpoints.txt
grep -rhoE '"/(auth|graphql|v1|v2)/[^"]*"' bundles/*.js | sort -u
wc -l endpoints.txt; head -n 40 endpoints.txt

The -h flag drops filenames, -o prints only the match, and sort -u turns hundreds of repeated references into one line per path. A path in five bundles is still one inventory entry.

Next I widen the search to the words around API calls:

grep -rhoE '"https?://[^"]+"' bundles/*.js | sort -u
grep -rhoE '(redirect_uri|client_id|grant_type|refresh_token|prelogin)[^",]{0,40}' bundles/*.js | sort -u
grep -rhoE '"(GET|POST|PUT|PATCH|DELETE)"' bundles/*.js | sort | uniq -c | sort -nr

Absolute URLs reveal other hosts the front end talks to. Each one gets the same scope question as a bundle URL: if it is out of scope, it goes in the notes as out of scope, not in the inventory.

3. Separate application routes from framework noise

Most of a bundle is not the application. Framework code, libraries, and shared chunks repeat the same strings everywhere, and a naive grep drowns the inventory in them. I separate the two by frequency and file name: vendor chunks repeat the same literals, while application chunks carry route strings that appear only a handful of times.

grep -rhoE '"(/[a-z0-9-]+){1,3}"' bundles/*.js \
  | sort | uniq -c | sort -nr | head -n 50

I read that list from the bottom up. The rare, specific strings are the application's own surface; the strings at the top, repeated hundreds of times, are usually framework plumbing. When a string is ambiguous, I search for it in context in the one bundle that contains it, instead of guessing from the grep output alone.

4. Turn the hits into an inventory, not a pile

Raw grep output is not an inventory. For each distinct path I record, in the dated engagement notes: the path, the bundle file it came from, any method or parameter seen next to it, and the status — unknown. Nothing else. No severity, no claim, no assumption that the path answers, requires authentication, or even still exists on the server. Bundles go stale, feature flags hide routes, and dead code ships.

I also record what I did not collect: pages behind a login I had not yet reached, chunks loaded only after an interaction, and any host I excluded as out of scope. When the session state changes — after a login, for example — I repeat the collection, because the authenticated bundle set is often larger than the public one.

What this gives you

After this pass I hold a map drawn by the application itself: its API paths, its version prefixes, its auth vocabulary, and the routes its front end knows about. Each later probe starts from a named endpoint with a recorded source, instead of from a guess. Rebuild the inventory every time the application redeploys — hashed filenames will tell you when it has.

Disclosure note. Techniques described here are methodology only. Specific findings from live engagements are reported privately to the vendor first and published here only after remediation or explicit permission.
