Webhooks: signatures and idempotency

A webhook is just an HTTP POST from someone else's server to yours. That simplicity is what makes webhook receivers a favorite target and, more importantly for us, a rich surface to read during recon. Here is how I think about webhook design — and how I verify a receiver that I am authorized to test.

Scope first. Everything below assumes written authorization for the target. No scope, no recon — that rule is non-negotiable in my workflow.

1. Signatures: the only trust mechanism that matters

A well-designed webhook carries a signature header — the sender computes HMAC-SHA256(payload, secret) and the receiver recomputes it before doing anything. No signature, no trust: without it, anyone who finds the endpoint URL can forge events.

Verifying by hand is one openssl call, and it is worth doing when you are testing your own receiver:

SECRET="whsec_test_shared_secret"
PAYLOAD='{"event":"payment.confirmed","ref":"TH-ABC123"}'
SIG=$(printf '%s' "$PAYLOAD" | openssl dgst -sha256 -hmac "$SECRET" | awk '{print $2}')
curl -s -X POST https://app.example.com/webhooks/payments \
  -H "Content-Type: application/json" \
  -H "X-Webhook-Signature: $SIG" \
  -d "$PAYLOAD" -w '\nHTTP %{http_code}\n'

Then replay the same request with a tampered byte in the payload, keeping the old signature. If the receiver still returns 200, it is not verifying — it is decorating its headers.

2. Compare the acceptance and the rejection

This is the response-comparison habit applied to webhooks. I fire four variants at my own receiver and record what comes back each time:

# 1. valid payload + valid signature
# 2. valid payload + wrong signature
# 3. tampered payload + original signature
# 4. no signature header at all

Cases 2, 3, and 4 should all be rejected, and ideally with the same response: a single rejection path. If "wrong signature" returns 400 but "missing signature" returns 200, the receiver has two code paths and one of them is a bypass.

Also watch for the classic mistake: hmac.compare_digest exists for a reason — a naive == on hex strings leaks a timing oracle. Reading the verification code is faster than measuring the oracle.

3. Replay: what a captured event buys an attacker

Signatures authenticate the sender, not the freshness of the message. An attacker who captures a valid signed event can replay it tomorrow and the signature will still check out. That is why serious senders add a timestamp to the signed payload:

curl -s -X POST https://app.example.com/webhooks/payments \
  -H "X-Webhook-Signature: $SIG_OLD" \
  -H "X-Webhook-Timestamp: $(date -d '2 days ago' +%s)" \
  -d "$PAYLOAD" -w '\nHTTP %{http_code}\n'

The receiver should reject timestamps outside a small window — five minutes is a sane default. When I test a receiver, I record the timestamp it accepted and replay the identical signed event an hour later. If the second call is processed as a new event, the receiver has no replay protection at all.

4. Idempotency: the receiver's own safety net

Even with perfect signatures and timestamps, senders retry. Networks drop ACKs, queues redeliver, and the same event can legitimately arrive twice. If processing the event twice credits an account twice, the bug is in the receiver's design.

The standard answer is an idempotency key: store the event ID when you first process it, and make re-processing a no-op. A quick way to check the behavior from the outside:

for i in 1 2 3; do
  curl -s -X POST https://app.example.com/webhooks/payments \
    -H "X-Webhook-Signature: $SIG" \
    -d '{"event":"payment.confirmed","id":"evt_9f27c1","ref":"TH-ABC123"}'
  echo " -- delivery $i"
done

The effect should happen exactly once no matter how many times you deliver. I once mapped this against a payment-integration testbed I control: three deliveries, one ledger entry. That invariant — "delivery N times, effect once" — is the whole contract. Everything else is implementation detail.

5. What to look for when the docs exist

Many providers publish their webhook signing scheme. When I am authorized to assess an integration, the provider docs tell me what to grep for in the receiver's code or behavior:

  • Which fields are included in the signed payload — raw body, or a canonical subset? Signing only some fields means the unsigned fields are attacker-controlled.
  • Whether the secret is per-integration and rotatable. One global secret for all merchants is a design smell worth noting.
  • Whether the receiver fetches the event back from the provider's API before acting on it — the strongest pattern, because the authoritative state comes from the provider, not from the POST body.

Why this is a recon topic

Webhook endpoints appear in JS bundles more often than you would expect — string-hunt for webhook, callback_url, or signature header names and you will find the receiver's URL before you even visit it. Reading that code path tells you how the application trusts the outside world, and trust boundaries are where findings live.

Test it at a human pace, one crafted request at a time, against targets you have permission to touch. The technique is cheap; the discipline is the point.
