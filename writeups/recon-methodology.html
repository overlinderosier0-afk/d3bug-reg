From crt.sh to JS bundles: a practical recon methodology

When I get authorized to test a target, the first hours decide everything. Good recon turns a black box into a map; bad recon turns it into a week of guessing. Here is the exact process I follow, with the commands I actually run.

Scope first. Everything below assumes written authorization for the target. No scope, no recon — that rule is non-negotiable in my workflow.

1. Subdomain enumeration via crt.sh

Certificate Transparency logs are the fastest free source of subdomains. One request, no API key, no rate-limit drama:

curl -s "https://crt.sh/?q=%25.example.com&output=json" \
  | jq -r '.[].name_value' \
  | sed 's/\*\.//g' | sort -u > subdomains.txt
wc -l subdomains.txt

The %.example.com pattern catches nested subdomains too. I keep this list in the engagement folder — it becomes the seed for everything else.

2. Separate the living from the dead

A list of 400 subdomains is noise. I resolve each one and keep only what answers. When the local DNS is unreliable (captive portals, filtered resolvers), I resolve over HTTPS instead of fighting the network:

curl -s "https://cloudflare-dns.com/dns-query?name=target.example.com&type=A" \
  -H "accept: application/dns-json" | jq -r '.Answer[].data'

Then pin the IP with curl --resolve so the rest of the tooling works even when the system resolver is broken.

3. Collect the JavaScript bundles

Modern apps ship their logic to the browser. That means the client tells you how the API works — endpoints, parameters, auth flows — if you read the bundles. I fetch the main pages, extract .js URLs, and download them locally:

curl -s https://target.example.com/ \
  | grep -oE 'src="[^"]+\.js[^"]*"' \
  | sed 's/src="//;s/"//' > bundles.txt

4. Grep for gold

With the bundles on disk, I hunt for structure with plain string searches before opening any file:

grep -rhoE '"/api/[^"]+"' *.js | sort -u          # endpoints
grep -rhoE '"https?://[^"]+"' *.js | sort -u        # absolute URLs
grep -roiE '(oauth|openid|token|refresh)[^"]{0,40}' *.js | sort -u

Keywords that almost always pay off: api/, v1/v2, oauth, prelogin, grant, redirect_uri, client_id. Each hit is a thread to pull.

5. Trace the auth flow, don't guess it

Login pages are where the interesting logic lives. Instead of guessing how credentials are transformed, I follow the code path from the submit handler:

  1. Find the login form's submit function (search for password near event listeners).
  2. Follow what happens to the password value — hashing? encoding? encryption?
  3. Note every network call in order: which endpoints, which parameters, what comes back.
  4. Check where tokens and session values end up: memory, storage, URL.

Crypto primitives are easy to spot even minified: CryptoJS, AES, SHA256, MD5, createHash. I map the sequence — input, transforms, output — because the sequence is what matters, not any single function name.

6. Probe at a human pace

Once I have candidate endpoints, I test them manually with curl — one request at a time, reading each response. No scanners, no fuzzing wordlists, no automated enumeration. On an authorized engagement this keeps the signal high and the noise (and risk) near zero.

A typical probe looks like this: hit the endpoint unauthenticated, then with a valid session, then with mutated parameters — and compare the responses. Identical responses to different inputs usually mean a dead end; different responses mean a thread worth pulling.

7. Write it down immediately

The unglamorous step that makes all the others compound. Every endpoint, every observed behavior, every dead end goes into the engagement notes the same day. Two weeks later, "I remember seeing something about a v2 endpoint" is worthless; a dated note is evidence.

What this gives you

After this process, I hold a map: the attack surface as the application itself describes it. Most findings I've worked on started as a single odd line in a bundle that only looked odd because I had the full map around it.

Recon is not a phase you finish. It is the background process that runs under everything else.

Disclosure note. Techniques described here are methodology only. Specific findings from live engagements are reported privately to the vendor first and published here only after remediation or explicit permission.
