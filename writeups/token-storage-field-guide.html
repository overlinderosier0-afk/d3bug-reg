Where tokens live: a field guide

Every authenticated session has to park its credentials somewhere on the client. Where a token lives — localStorage, a cookie, page memory, the URL — changes what you can observe, how you reproduce a session in curl, and which questions are even worth asking. This is my inventory routine: the same five places, checked in the same order, on my own accounts, during authorized engagements.

Scope first. Everything below assumes written authorization for the target and is done with your own test accounts. No scope, no probing — that rule is non-negotiable in my workflow.

1. localStorage — the honest key-value drawer

Open DevTools, go to Application → Local Storage, and look. Tokens here persist across tabs and restarts, and the keys are usually self-descriptive: access_token, id_token, authToken, user containing a JSON blob. From the console I list keys before assuming anything:

// in DevTools console, on your own session
for (let i = 0; i < localStorage.length; i++) {
  console.log(localStorage.key(i));
}

What I record: the key names, whether the values are JWTs or opaque strings, and what happens to them on logout (cleared? left behind?). A token that survives logout is a note worth keeping — on my own session, it tells me how the app treats session lifecycle.

2. sessionStorage — same drawer, tab lifetime

Application → Session Storage. Same inspection method, but the lifetime rule is different: everything vanishes when the tab closes. Apps that use it tend to be more careful, and it changes my reproduction workflow — I can't rely on a token captured yesterday still being valid. The check is identical in the console:

for (let i = 0; i < sessionStorage.length; i++) {
  console.log(sessionStorage.key(i));
}

3. Cookies — read the flags, not just the names

Cookies live in Application → Cookies and in the Set-Cookie headers of the login response. The names matter less than the flags. My checklist for each session cookie:

$ curl -s -D headers.txt -o /dev/null -X POST \
    https://app.example.com/api/login \
    -H "Content-Type: application/json" \
    -d '{"user":"my-test-account","pass":"..."}'
$ grep -i "^set-cookie" headers.txt

I look at HttpOnly (readable from JS or not), Secure, SameSite, and the Path. A cookie without HttpOnly is readable via document.cookie — that's an app design choice I note, not a finding I announce. For reproduction in curl, cookies mean using a cookie jar instead of copying an Authorization header:

$ curl -s -b cookies.txt https://app.example.com/api/profile | jq .

4. Memory — the token that only exists at runtime

Some apps keep tokens only in JavaScript variables: nothing in storage, nothing in cookies, reload the page and you log in again. You confirm this by elimination — storage is empty, cookies carry nothing, yet requests carry an Authorization: Bearer … header in the Network tab. I trace where the header gets attached, usually an interceptor or a fetch wrapper found by searching the bundle for Authorization:

grep -rhoE "Authorization[^,;]{0,60}" *.js | sort -u

Memory-stored tokens are the hardest to reuse in curl: you copy the bearer value from a captured request, use it, and watch how long it stays valid. Expiry and rotation behavior — does it silently refresh? — is exactly what I document here.

5. The URL — the place tokens should never be

Check the address bar and the redirect chain after login. Tokens in query parameters or fragments end up in browser history, proxy logs, and Referer headers — all places outside the app's control. I watch the Network tab during the login redirect sequence and flag any token-shaped value in a URL as a design concern to document:

$ curl -s -D - -o /dev/null \
    "https://app.example.com/api/oauth/authorize?client_id=…" \
    | grep -iE "location|token"

The Location header of each redirect is the thing to read. If a session value rides along in it, that goes in the notes — factual, no drama.

The inventory, as a routine

On a new engagement the sequence is always the same, on my own account:

  1. Log in, then list localStorage and sessionStorage keys.
  2. Inspect Set-Cookie headers and cookie flags.
  3. Check whether requests carry a bearer header — and where it comes from.
  4. Watch the URL bar and redirect Location headers through the whole login flow.
  5. Log out and re-check every location: what survived, what rotated, what vanished.

Five minutes of routine, and I know exactly how to carry the session into curl for the manual probing that follows — jar file or copied header, fresh token or long-lived one. That knowledge is unglamorous and it saves hours.
