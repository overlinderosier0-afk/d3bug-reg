Observing rate limits without tripping them

Rate limiting is a defense you meet long before you go looking for it. Send a few login probes in a row during normal manual testing, and at some point the server answers with something other than a login result. That moment — the 429, the slowed response, the Retry-After header — is free information about how the target defends itself. This post is about noticing it, reading it, and writing it down, without ever trying to get past it.

Scope first. Everything here assumes written authorization for the target. No scope, no recon.

1. The signs, in order of subtlety

Rate limiting shows up in layers. From most explicit to most quiet:

  1. 429 Too Many Requests — the server tells you outright.
  2. Retry-After header — a number of seconds, or an HTTP date, telling well-behaved clients when to come back.
  3. X-RateLimit-* headers — Limit, Remaining, Reset: the defense documenting itself in every response.
  4. Soft signs — responses that suddenly take longer, a challenge page that only appears after several attempts, an endpoint that keeps returning 200 but with an empty body.

The first three are documentation. The last one is the interesting one.

2. Read the headers with curl

When a request behaves oddly, look at the response headers before anything else:

$ curl -sSI https://target.example.com/api/v1/login \
  | grep -iE 'ratelimit|retry-after|HTTP'
HTTP/2 429
retry-after: 60
x-ratelimit-limit: 10
x-ratelimit-remaining: 0
x-ratelimit-reset: 1760510400

That response says: 10 requests per window, the window is spent, come back in 60 seconds. The x-ratelimit-reset value is a Unix timestamp — translate it:

$ date -d @1760510400 -u
Wed Oct 15 14:40:00 UTC 2026

Now you know exactly when the window resets, and you can schedule the rest of your manual testing around it instead of hammering into a closed door.

3. Soft limits are limits too

Some applications never send a 429. They throttle quietly: each consecutive response takes a little longer, or a bot-mitigation challenge appears only after the Nth attempt on the login endpoint. To check the timing hypothesis, compare response times rather than relying on feel:

$ curl -s -o /dev/null -w "%{time_total}s\n" https://target.example.com/api/v1/login
0.212s
# ... a few manual attempts later ...
$ curl -s -o /dev/null -w "%{time_total}s\n" https://target.example.com/api/v1/login
2.431s

A jump from 0.2s to 2.4s on the same request is a signal. It tells you a throttle kicked in even though the status code never changed. Same rule as with hard limits: note it, wait, and move on — do not keep probing to "confirm" the pattern.

4. Compare across endpoints

One limit in isolation means little. Do the same small handful of manual requests against different endpoints and note which ones enforce limits and which do not — login, password reset, search, static assets. The pattern is the information:

  • Strict limits on auth endpoints, none on search: the team thought about credential stuffing.
  • Different limits per endpoint: a real rate-limiting layer, not one global bucket.
  • Limits keyed differently per endpoint (IP vs. session vs. account): the defense has layers, and each layer shapes how you pace your manual tests.

This is observation during normal testing, not a measurement campaign. My rule is simple: the moment I suspect a limit, I stop, note it, and test something else. I never run a loop to find the exact threshold. The exact number is almost never the interesting question — the differences between endpoints are.

5. Write it in the notebook

Rate-limit observations go straight into the engagement notes the same day they happen. My endpoint inventory has a "limits" column:

endpoint              | limit seen            | headers seen          | date
/api/v1/login        | 429 after ~10 tries   | retry-after: 60       | 2026-10-15
/api/v1/search       | none in normal use    | -                     | 2026-10-15

And the dead-end log gets one line: "429 on login at 14:32 — waited for the window, continued with search instead." Two weeks later, that line tells you exactly how to pace the retest. Memory would have said "something about a rate limit, I think."

6. What rate limits tell you about the defense

Read as a system description, rate limiting is the target telling you where it expects to be hit:

  • Limits on auth endpoints suggest the team expects brute-force and credential-stuffing attempts.
  • Standard headers (Retry-After, X-RateLimit-*) suggest a mature stack — off-the-shelf middleware or a deliberate API design.
  • Soft throttling with no headers suggests a WAF or bot-mitigation layer sitting in front of the application.
  • The absence of any limit in normal use means exactly that — nothing more. It is not a finding, it is a gap in your observations, and you treat it as one.

Rate limits are the target describing its own threat model. Read the description, note it with a date, and keep testing like a guest who does not want to be asked to leave.
