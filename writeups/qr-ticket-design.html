Designing tamper-evident QR tickets

A QR code on a ticket is just a picture of a string. If the string is ticket=12345, anyone can print their own. The security of a QR ticket does not live in the code itself — it lives in the design around the payload: signatures, expiry, and single-use semantics. Here is how I think about each layer, with commands to try on a terminal.

Scope first. Everything here assumes written authorization for the target. No scope, no recon.

1. Sign the payload, don't just encode it

The foundation is an HMAC signature. The payload is a small JSON object (ticket id, event id, issued-at timestamp), and a secret known only to the issuer produces a tag over it. The QR carries payload + signature, and the scanner verifies the tag before trusting anything else.

Generate and verify a tag locally to see the mechanics:

$ payload='{"ticket":"T-0042","event":"E-7","iat":1760275200}'
$ echo -n "$payload" | openssl dgst -sha256 -hmac "server-side-secret"
SHA2-256(stdin)= 9f2c...truncated
$ echo -n "$payload" | openssl dgst -sha256 -hmac "wrong-secret"
SHA2-256(stdin)= 4b1d...truncated

Change one character in the payload and the tag changes completely. That is the property you are buying: the check-in app can detect any alteration without trusting the ticket holder. The one non-negotiable rule is that the signing secret never leaves the server — if a client-side bundle can sign tickets, the whole design collapses. I verify secrets are server-only by grepping shipped bundles for the key name used in signing code (see reading-minified-js).

2. Bind the ticket to an expiry window

A valid signature is not enough if the ticket is valid forever. Include an expiration claim inside the signed payload so that even a leaked screenshot stops working after the event:

$ python3 -c "
import hmac, hashlib, json, time
key = b'server-side-secret'
payload = json.dumps({'ticket':'T-0042','event':'E-7',
                      'iat': int(time.time()),
                      'exp': int(time.time()) + 6*3600})
tag = hmac.new(key, payload.encode(), hashlib.sha256).hexdigest()
print(payload + '.' + tag)
"

The check-in flow becomes: verify signature, then check now < exp, then check the ticket has not been scanned already. Expiry also bounds the damage of a lost phone — a ticket issued months ahead is dangerous; a ticket whose window covers the event plus a grace period is not.

3. Single-use semantics: scan once, then burn

Signatures and expiry stop forgery. They do not stop copying. A screenshot of a valid ticket scans green just as well as the original. The fix is server-side state: the first scan marks the ticket used, and every later scan of the same ticket id is rejected.

The state transition has to be atomic — mark-used must happen inside the same database transaction as the read, or two scanners at two entrances will both wave the same screenshot through. Offline scanners are the hard case: pre-distribute the list of issued ticket ids with their signatures, validate locally, and reconcile against the central "used" set as soon as connectivity returns. The offline copy must never include the signing secret, only the issued tags.

4. What I check when I review a QR ticket design

When an authorized engagement touches ticketing, I walk this checklist:

  • Is the payload signed with a server-side key? (unsigned QR = raw identifier; decode it with zbarimg and read the string)
  • Is there an expiry claim, and is it enforced — or just present?
  • Is a used ticket rejected on a second scan, from a different device and a different network path?
  • Does the check-in app fail closed — invalid signature means reject, not retry or fallback to a "manual override"?
  • Are ticket ids unguessable (random, not sequential) so one valid ticket can't seed the next?

Each question maps to one human-paced request pair: scan a ticket, then replay or mutate it and compare the responses. Status codes and error messages tell you whether the design holds.

5. What NOT to put in the payload

QR contents are visible to everyone who photographs the screen. Never encode PII beyond the minimum (a ticket id is enough — names, phone numbers, and emails belong behind the scanner's lookup), never encode the event's internal database row, and never encode anything that looks like a credential or a reset token. The payload is a public string; treat it like one.
