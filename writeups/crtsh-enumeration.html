Subdomain enumeration with crt.sh

Before I send a single probe, I want a map of the target. Subdomain enumeration is how I build the first version of that map, and Certificate Transparency logs are the fastest free source for it. One public query returns the names that have appeared on certificates for a domain — no account, no API key, no scanner. This post covers the query I run, how I clean the result, and how I turn it into a target list I can trust.

Scope first. Everything here assumes written authorization for the target. No scope, no recon.

1. Why certificate transparency

When a certificate authority issues a certificate, the certificate is normally logged in public Certificate Transparency logs. Each log entry names the domains the certificate covers. That makes the logs a public, queryable record of names an organization has put certificates on: the main site, its API hosts, staging environments, and services that were never linked from anywhere. I am not guessing names or brute-forcing wordlists. I am reading a public log. The query is one ordinary HTTPS request, it touches no target infrastructure, and it produces a list I can review before deciding anything else.

2. One query, no API key

The query uses crt.sh, the public Certificate Transparency search interface. The %25. prefix is the URL-encoded wildcard, so the search returns nested subdomains as well as direct ones, and output=json gives structured data I can filter with jq:

curl -s "https://crt.sh/?q=%25.example.com&output=json" \
  | jq -r '.[].name_value' \
  | sed 's/\*\.//g' | sort -u > subdomains.txt
wc -l subdomains.txt

Three details in that pipeline do real work. First, name_value can hold several names separated by newlines, so jq -r expands one entry into several lines. Second, sed 's/\*\.//g' strips the wildcard prefix, turning *.api.example.com into api.example.com — the name I would actually resolve. Third, sort -u deduplicates: the same name appears on many certificates, and a list with each name repeated twenty times is noise. I save the result to subdomains.txt in the engagement folder, with the date in my notes, because this file becomes the seed for everything that follows.

3. Clean the list before you trust it

The raw output is never ready to use as-is. I read it first, then clean it deliberately. Entries outside the authorized scope go out immediately, even if they look interesting — scope is decided in writing before recon starts, not renegotiated because a name looks promising. I also check for casing and trailing whitespace, for names that belong to a different domain that merely shares a suffix, and for entries that are clearly not hostnames. A short manual pass now is cheaper than chasing a phantom host later:

grep -v '\.example\.com$' subdomains.txt   # anything that should not be here
sort -u subdomains.txt -o subdomains.txt
wc -l subdomains.txt

4. Separate the living from the dead

A list of hundreds of names is still mostly noise. Many certificates outlive the services they covered, and many names resolve to nothing. So the next step is resolution: keep only the names that answer. When the local resolver is unreliable — a filtered network, a captive portal — I resolve over HTTPS instead, one name at a time:

curl -s "https://cloudflare-dns.com/dns-query?name=api.example.com&type=A" \
  -H "accept: application/dns-json" | jq -r '.Answer[].data'

A name with no answer is a dead end for now, and I note it as such rather than deleting it silently: a name that is dead today may not be dead next month. For names that do answer, I pin the resolved IP with curl --resolve so the rest of the tooling keeps working even when the system resolver is broken. Only the living, in-scope names move on to the next phase.

5. What crt.sh does not show you

This method has honest limits. It only finds names that appeared on certificates, so a service with no certificate will not appear. It shows history as well as the present, so retired names sit next to live ones until resolution sorts them out. And a wildcard entry tells me a pattern exists, not that any particular host under it does. None of that makes the list useless — it makes it a starting point. I treat subdomains.txt as a hypothesis to verify, not as a proven inventory, and I never present a name from this list as vulnerable or exposed. It is a name on a public log, nothing more, until I have observed something myself, inside scope, at a human pace.

6. Feeding the next step

The cleaned, resolved list is the input to the rest of recon. The live hosts are where I collect JavaScript bundles and grep them for endpoints, and where I trace auth flows in minified code — the steps covered in earlier posts in this series. A sloppy list here propagates everywhere: a missed name means a missed bundle. That is why the first hour of an engagement is mostly this quiet work — one query, a careful cleanup, resolution, notes. Just a map, built from a public record, checked name by name, and written down before anything else happens.
