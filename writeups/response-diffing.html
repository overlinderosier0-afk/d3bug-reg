Diffing responses to find the interesting ones

Most of my manual testing is comparative. I send one request, save the response, change exactly one thing, send it again, and compare the two answers side by side. The server usually tells you whether a parameter matters — not in words, but in the difference between two responses. Response diffing is how I listen for that difference without guessing.

Scope first. Everything below assumes written authorization for the target. No scope, no testing — that rule is non-negotiable in my workflow.

1. Capture a baseline first

A diff is only meaningful if the first response is a known good one. Before I mutate anything, I capture the baseline: the request exactly as the application itself sends it, with a valid session where one is needed, saving both body and headers to files. Reading a response in a terminal and trying to remember it is not a baseline. A file is.

curl -s "https://target.example.com/api/profile" \
  -H "Authorization: Bearer $TOKEN" \
  -o baseline.body -D baseline.headers \
  -w "%{http_code} %{size_download}\n"
cat baseline.body | head -c 600; echo

The -w line gives me the status code and the size at a glance. A sudden size change is often the first hint that a mutation did something, though size alone is crude — two responses can be the same length and completely different. The files are what I actually compare later.

2. Change exactly one thing

The discipline of diffing is the discipline of the single variable. If I change the parameter, the session, and the headers all at once, a different response tells me nothing about which change caused it. So I copy the baseline request and change one parameter, one header, or one value — and nothing else:

curl -s "https://target.example.com/api/profile?view=summary" \
  -H "Authorization: Bearer $TOKEN" \
  -o mutated.body -D mutated.headers \
  -w "%{http_code} %{size_download}\n"
diff -u baseline.body mutated.body | head -60

I run the same pattern for the other comparisons that matter: unauthenticated versus authenticated, one role versus another, a parameter present versus removed. Each pair is one question, answered by one diff. When a diff is empty, that is an answer too: the input I changed had no observable effect here. I note it and move on instead of retrying the same mutation louder.

3. Normalize before you compare

Raw diffs lie. Timestamps, request IDs, CSRF tokens, and session cookies change on every response, and they will fill a diff with noise that hides the one line that matters. Before comparing JSON bodies, I normalize them: sort the keys, pretty-print them, and drop the fields that are different every time. The same idea applies to headers — date and set-cookie lines are expected to move.

jq -S 'del(.timestamp, .requestId, .traceId)' baseline.body > baseline.norm
jq -S 'del(.timestamp, .requestId, .traceId)' mutated.body > mutated.norm
diff -u baseline.norm mutated.norm

grep -viE '^(date|set-cookie|x-request-id):' baseline.headers > baseline.hdr
grep -viE '^(date|set-cookie|x-request-id):' mutated.headers > mutated.hdr
diff -u baseline.hdr mutated.hdr

Normalizing is a judgment call, and I write down which fields I dropped. If I delete a field from both sides, I cannot later claim it never changed. The normalized files are a working view; the raw files stay untouched so I can always go back and check what I filtered out.

4. Read the diff, not just its length

A short diff can be the most interesting result of the day, and a long diff can mean nothing. I look for, in order: a status-code change, a different error message or code, a field that appears or disappears, a value that changes shape — a string becoming a number, an object becoming null, a list gaining an entry. Those structural differences are where behavior shows. A long diff of only reordered keys or fresh timestamps is noise, and normalizing usually removes it.

I also compare what is absent. If the baseline returns a field and the mutated response drops it silently, or a specific error becomes generic, that change in shape is information even when no new data appears. A different response is never proof of a vulnerability — only a thread, a reason to read the surrounding code and decide whether a careful follow-up is warranted.

5. Keep the pairs, and keep them dated

Every comparison gets a small, boring folder discipline: baseline and mutated files with matching names, a one-line note saying what changed and what the diff showed, and the date. Two weeks later, "the profile endpoint behaved oddly" is worthless. A dated note — "2026-10-30: view=summary dropped the email field, status stayed 200" — is something I can act on, reproduce, or close.

mkdir -p notes/2026-10-30-profile-view
cp baseline.body mutated.body notes/2026-10-30-profile-view/
echo "view=summary: email field absent, status 200 both sides" \
  >> notes/2026-10-30-profile-view/README

This is slow work by design. One request at a time, one diff at a time, every response actually read. It keeps the signal high, the noise near zero, and the notes honest — because the notes describe responses I saved, not responses I half-remember.

What this gives you

Response diffing turns vague curiosity into a repeatable test: same request, one change, saved files, a normalized diff, a dated note. Most dead ends are found this way, cheaply, in seconds — and the threads that survive the diff are worth the slower work that follows. When a response does not change, believe it. When it does, read the exact lines that changed before deciding what they mean.
