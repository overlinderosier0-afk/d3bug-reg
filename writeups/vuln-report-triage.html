Triaging a vulnerability report in 15 minutes

A report arrives, and the first instinct is to believe it or dismiss it. Both are mistakes. Triage is a short, written decision about whether a report earns more time, and why. Fifteen minutes is enough when the questions are fixed in advance: investigate, reject, or ask for the missing evidence.

Scope first. Everything here assumes written authorization for the target, and that any reproduction happens inside that scope, at a human pace. No scope, no reproduction — that rule is non-negotiable in my workflow.

Minutes 0–2: extract the threat model

Read the report once and write one sentence: an attacker with a stated capability can take a stated action to obtain a stated impact. If that sentence cannot be written, the report is not ready to judge. Vague claims are not a threat model. The sentence forces the report to name who attacks, with what access, and what changes for the victim.

Two checks belong in these first minutes. First, is the claimed capability smaller than the claimed impact? If the attacker already needs the very access the flaw would supposedly grant, the report is redundant. Second, is the behavior reachable in real use — called from real code, enabled by real configuration — or only in theory? A path no real deployment exercises is a code smell, not a finding.

Minutes 2–7: reproduce, or mark it unreproduced

Open a dated triage note first. The note is the deliverable:

mkdir -p triage
cat > triage/report-id.md <<'EOF'
# Triage — report-id
- Claim:
- Threat model:
- Reproduction tried:
- Verdict:
EOF

Then try the reporter's steps exactly as written, once, at a human pace, on an authorized target, reading each response. If a step is missing or ambiguous, stop and write that down instead of improvising a different attack — improvisation turns triage into new research, which has no fifteen-minute budget.

A reproduction that produces the claimed behavior is evidence. One that produces nothing is also evidence — of a gap, not of safety. Record exactly what was tried, including inputs and responses observed, so anyone can repeat the attempt and get the same result.

Minutes 7–10: scope and impact, in that order

Scope first: does the affected component fall inside the written authorization? A real flaw outside scope is noted, set aside, and handled through the proper channel — not triaged into an investigation. Impact second: what does the attacker gain, and who is harmed? Rank it by the concrete outcome — data exposed, actions performed as another user, state changed without authorization — not by the severity label on the report. A CVE number or CVSS score proves nothing on its own. And ask whether the behavior is standard or documented: correct implementation of a specification, or explicitly documented behavior with security warnings, is not a vulnerability of that component.

Minutes 10–13: weigh the evidence, list the gaps

By now the report has either survived or it has not. Answer each remaining question in the note:

  1. Is the threat model complete — attacker, capability, path, impact?
  2. Does the attacker gain something they did not already have?
  3. Is the path reachable in real deployments, not just in theory?
  4. Is the behavior a deviation from the standard or the documentation, rather than a correct implementation of either?
  5. Would fixing it cost more — in risk, disruption, or ecosystem impact — than the flaw itself? If so, the severity drops.

The burden of proof sits with the reporter. It is not the triager's job to prove a claim unexploitable. When evidence is missing, name the exact evidence that would close the gap: a reproduction step, a log line, a configuration detail. "More details, please" helps nobody; a precise list does.

Minutes 13–15: decide, and write the decision down

There are only three outcomes. Investigate when the report survives every check: escalate it, build a proper proof of concept, and write the finding. Reject when a check fails: close it with the precise reason written in the note, so the same report does not come back unchanged. Request evidence when a check cannot be judged: send back only the list of missing proof. A rejected report with a documented justification is worth more than a false positive in a deliverable.

Watch for the two classic errors. Rejecting a valid report for a bad reason — "only local access" is a real threat model in multi-tenant and containerized deployments. And accepting an invalid report for a bad reason — a CVE exists, the score is high, or fixing it "just in case" feels safer. The first buries real risk; the second spends the vendor's trust.

Why the timer matters

Fifteen minutes is not about speed. It is about forcing the decision to be small, written, and checkable. A report that needs more than fifteen minutes has already earned its investigation — that is the point of the timer. A report that cannot survive fifteen minutes of fixed questions has told you everything you need to know, and the note proves it.
