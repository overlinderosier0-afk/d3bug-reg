Secrets in git history: a researcher's view

Every researcher has a moment where git log turns up something that should never have been committed. A .env file with a production API key. An old commit adding config.py with a database password. The file was deleted two commits later — and the secret is still sitting in history, readable by anyone who can reach the repository. Git is append-only by design: a committed secret stays committed until history itself is rewritten. Here is how I audit a repository's history for leaked secrets, using only git — on my own repos, or on repos I am authorized to assess.

Scope first. This is audit methodology. It applies to repos you own or repos you are authorized to assess. Reading public history is reading public information — mining it for credentials to use is not research. If you find a live secret belonging to someone else, the move is disclosure, not use.

1. Why deleting the file is not enough

git rm .env removes the file from the working tree and from future commits. It does nothing to the commits that already contain it. Any version of the file is one command away:

git show 9f3a2b1:.env

Forks, CI logs, clones on old laptops, and archive mirrors keep copies you will never reach. That is the first rule of secret hygiene: once a credential touches git history, assume it is compromised and rotate it. Rewriting history is cleanup; rotation is the fix.

2. What to look for

Filenames first — they are the cheapest signal:

.env, .env.local, .env.production
config.json, settings.py, .npmrc, .pypirc
credentials.json, *.pem, id_rsa, .aws/credentials
.git-credentials, docker-compose.yml with inline passwords

Then content patterns — strings that look like secrets:

API_KEY, api_secret, password =
BEGIN RSA PRIVATE KEY, BEGIN OPENSSH PRIVATE KEY
ghp_, sk_live_, AKIA
mongodb://user:pass@, postgres://user:pass@

3. Searching history with git

Git ships everything you need to audit history. My sequence:

$ git log --oneline --all | head -30      # get the lay of the land
$ git log --all --full-history -- ".env"   # which commits ever touched .env?
$ git show 9f3a2b1:.env                    # inspect the file as of that commit

Then the pickaxe — -S finds commits that added or removed a string, -G does the same with a regex:

$ git log -p -S "API_KEY" --all            # commits that added/removed this string
$ git log -p -G "password\s*=" --all        # commits matching this pattern

And for content that log might miss, git grep across every revision at once:

$ git grep "BEGIN RSA PRIVATE KEY" $(git rev-list --all)   # every commit, one search

These commands are the audit. They tell you what leaked and when — they do not fix anything. The fix is always rotation first.

4. The researcher's angle

During an authorized engagement, a client's public GitHub presence is part of the attack surface: public repos, gists, old forks, archived projects — all of them carry history. The workflow is the same one I run on my own repos: enumerate the public repositories, fetch them, and run these searches locally.

What goes in the engagement notes: the exact commit hash, the file, the line. Dated, factual, minimal. The secret itself is never used to log in anywhere, never pasted into chat, never left in a note unredacted. Then it goes to the owner with rotation steps, like any other finding — reported privately, published here only after remediation or permission.

5. Prevention is a five-second habit

Keep secrets in environment variables or a secret manager, never in files that could be committed. .gitignore the obvious entries:

*.env
*.pem
id_rsa*
.aws/
.git-credentials

And audit before every push — git status and git diff --cached take five seconds and have saved me more than once. I once had to revoke a token after it touched a repo. Rotation took minutes; the lesson stuck: the audit happens before the push, not after.

What this gives you

A repo you can hand to anyone — contractor, contributor, auditor — without worrying about what is buried in its history. Audit your own repos the same way you would audit a client's: systematically, with dates, and with the fix (rotation) already decided before you start searching.

Disclosure note. If an audit turns up a live credential belonging to a third party, report it to the owner first — privately, with rotation steps — and publish nothing until it is remediated or the owner agrees.
