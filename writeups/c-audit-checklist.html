A C code review checklist

C gives the reviewer no safety net: no bounds checker, no garbage collector, no runtime to catch a bad assumption before it becomes a crash. That is why a C review should never be a single skim. I review in passes, one bug class at a time, in the same order every time. Each pass asks one question, and a file is not done until every pass has answered it.

Scope first. Everything here assumes written authorization for the target. No scope, no recon.

1. Map the inputs before reading the logic

Start with the surface, not the algorithm: every place untrusted data enters — command-line arguments, files, network reads, environment variables, any value crossing a trust boundary. Note which functions receive that data and how far it travels before validation.

grep -rn "argv\|getenv\|fread\|recv\|read(" --include="*.c" .
grep -rn "int main\|parse_\|handle_" --include="*.c" --include="*.h" .

For each input, write down where it comes from, what type and size it is expected to be, and where it is first checked. If any of the three is unclear, that is the first review note: an open question to resolve before judging the code around it.

2. Buffers: who sets the length, and who checks it?

For every copy, ask where the destination size comes from and where the source length comes from. The dangerous pattern is not one function name; it is a copy whose length is assumed rather than derived from the destination. Check the unbounded classics first, then the bounded ones: a bounded call with a wrong bound is just as broken:

grep -rn "strcpy\|strcat\|sprintf\|gets(" --include="*.c" .
grep -rn "strncpy\|strncat\|snprintf\|memcpy\|memmove" --include="*.c" .

On the bounded calls, verify three details: the size argument really is the destination size, the return value is checked where it matters (snprintf reports truncation instead of failing), and the result is NUL-terminated on every path. Watch the off-by-one: a buffer of size N holds N - 1 characters plus the terminator, and a loop running to <= N has already gone too far.

3. Integers: check the arithmetic, not just the value

Integer bugs hide in the arithmetic done before a check. A length validated after it has been multiplied, added, or cast can wrap around and pass a check it should have failed. Review every size calculation feeding an allocation or a copy: a count multiplied by an element size, a header length added on, any conversion between signed and unsigned types. For each one, ask: can this computation overflow before the result is used, and is the check placed before that computation? Prefer size_t for sizes, keep signed and unsigned values apart in comparisons, and treat any narrowing cast as needing an explicit range check first.

4. Memory lifetime: who owns it, and when does it die?

For every allocation, trace the lifetime: who allocates it, who frees it, and whether any pointer survives the free. The recurring classes are use-after-free, double-free, freeing a pointer that was never allocated, and returning the address of a stack variable. Trace ownership across function boundaries, because that is where it breaks — a function that frees memory its caller still uses, or a caller that frees memory already freed on an error path. Error paths deserve the same attention as the happy path: a function that allocates three buffers and frees only two when the third allocation fails leaks on exactly the path nobody tested.

grep -rn "malloc\|calloc\|realloc\|free(" --include="*.c" .
# for each free(): is the pointer used again? is it freed twice?

When a pointer is stored in a struct or a global, note who owns it next to the declaration. Ownership written down there is the cheapest defence against a lifetime bug three hundred lines later.

5. Dangerous APIs and format strings

Finish with the calls that turn a logic bug into something worse: a format string from input, a shell command built by concatenating untrusted text, a file path assembled from user input. All are the same problem: data reaching a place where it is interpreted as instructions.

grep -rn "printf\|fprintf\|sprintf\|snprintf" --include="*.c" .
grep -rn "system(\|popen(\|execl\|execv" --include="*.c" .

Every format call should have a literal format string, with input passed as arguments. Every shell or process call should be questioned even when the input looks trusted — trusted today is not trusted after the next refactor.

6. One pass, one question — then verify

Run the passes in this order — inputs, buffers, integers, lifetime, dangerous APIs — and take notes per pass, not per file. A note should record the file and line, the question that raised it, and what would have to be true for it to be safe. That last part matters: most notes collapse on re-reading because the reviewer never wrote down the assumption. Before calling a pass finished, let the compiler help:

gcc -Wall -Wextra -Wshadow -fanalyzer -c file.c -o /dev/null
# read every warning; a warning you cannot explain is a review note

Compiler warnings are not findings, and a clean build is not a clean bill of health. They are a second pair of eyes on the passes you just made.

What the checklist buys you

A checklist does not make a review exhaustive. It makes it repeatable: the same questions, in the same order, on every file, so the bug class you would have skipped on a tired afternoon gets checked anyway. Review slowly, write the assumption down, and let the passes decide when a file is done.
