Hardware debugging notes: UART on ESP32

Most of my notes here are about web recon, but the lab has a hardware side too: Arduino, ESP8266, ESP32 boards wired to sensors and servos. When hardware misbehaves, the single most useful diagnostic is also the simplest — the serial console. UART is the curl of embedded work: one channel, plain text, and it tells you exactly what the device thinks it is doing.

Scope first. Everything here is my own hardware — boards I own, firmware I wrote or flashed myself. The same rules as the rest of this blog apply: no scope, no recon.

1. Know what UART is, physically

UART is asynchronous serial: two data wires, TX (transmit) and RX (receive), plus a shared ground. TX of one side goes to RX of the other — never TX to TX. No clock wire, so both sides must agree on the baud rate or the output is garbage. On an ESP32 devkit the USB port already includes a serial adapter wired to the chip's hardware UART0, so you get a console for free the moment you plug the board in.

2. Find the pins on an unknown board

Checklist, in order:

  1. Schematic or silkscreen. Labels like TX, RX, or UART are the fastest win.
  2. Idle voltage. An idle UART TX pin sits HIGH — 3.3 V on ESP32-class logic. Probe candidate pins with a multimeter while the device boots: a pin parked at 3.3 V that twitches when the device starts talking is TX.
  3. Common ground first. Connect GND before any data wire. Half of all "UART is broken" sessions are just two circuits floating at different references.
  4. Cross the data wires. Your adapter's RX goes to the device's TX and back. Never connect a 5 V TX to a 3.3 V RX without a level shifter.

3. Sweep the baud rate

The classic symptom of a wrong baud rate is garbage: rows of ⸮⸮⸮⸮ where text should be. Garbage means the wiring is probably right and the timing is wrong — that is progress. The ESP32 boot ROM always speaks 115200, so a freshly reset board prints its boot header at 115200 no matter what the app later switches to. My sweep order:

115200    # ESP32 / ESP8266 app and boot ROM default
9600      # sensors, GPS modules, classic peripherals
57600     # older firmware defaults
74880     # ESP8266 boot ROM oddity
460800    # fast flash/debug links

Method: open the monitor at one rate, reset the board, and watch. Readable header means the right rate. Identical garbage on every reset means the rate is wrong but the wiring is good — move to the next rate. Different random garbage each time points back at the wiring.

4. Open the serial monitor

First, find the device node. On Linux a CP210x or CH340 USB-serial adapter shows up as /dev/ttyUSB0:

$ dmesg | tail -5
usb 1-2: cp210x converter now attached to ttyUSB0

Then open the monitor at the firmware's baud rate. arduino-cli covers both upload and monitoring without a GUI:

$ arduino-cli monitor -p /dev/ttyUSB0 -c baudrate=115200

If arduino-cli is not handy, screen does the same job and is on almost every system:

$ screen /dev/ttyUSB0 115200
# detach with: Ctrl-a, then k, then y

One port, one process: if the monitor fails with "device busy", something else is holding the port — a previous monitor session, a browser tab with Web Serial, or an upload in progress.

5. Read the boot log

Reset the board while the monitor is open. A healthy ESP32 prints something like:

rst:0x1 (POWERON_RESET),boot:0x13 (SPI_FAST_FLASH_BOOT)
configsip: 0, SPIWP:0xee
clk_drv:0x00,q_drv:0x00,d_drv:0x00,cs0_drv:0x00,hd_drv:0x00,wp_drv:0x00
mode:DIO, clock div:2
load:0x3fff0030,len:4544
entry 0x400806b4

This header is the hardware's own status report. rst tells you why the chip restarted (power-on, software reset, watchdog, brownout). A boot entry showing download mode instead of SPI_FAST_FLASH_BOOT means the GPIO0 strapping pin was held low and the chip is waiting for an upload instead of running your firmware — which explains an otherwise "dead" board. Read the first five lines before touching anything else; they answer most "it won't start" questions.

Note that the application can switch baud rates after boot: the boot header stays readable at 115200, but if the sketch uses a different rate its own output turns to garbage. When the header is clean but the rest is noise, match the app's configured rate — check the Serial.begin() call.

6. Common traps, from my logbook

  • Garbage only after boot: wrong app baud rate — check the Serial.begin() call.
  • Nothing at all, port opens fine: TX/RX swapped, or the firmware never calls Serial.begin().
  • Board resets in a loop: read the rst reason on each boot; watchdog and brownout resets repeat with a visible pattern.
  • Upload fails but the monitor works: GPIO0 strapping — hold the BOOT button while starting the upload, release once flashing begins.

The serial console is the cheapest observability a board gives you: one USB cable, the right baud rate, and the habit of reading the first five lines before changing anything. Same discipline as web recon — and like web recon, the winning move is writing it down. The baud rate that worked, the pins actually wired, the boot log's rst reason: all in the dated lab notes, the same day.
