When esptool says the port is busy

Every flashing session eventually hits it. You run esptool, and instead of a progress bar you get:

$ esptool.py --chip esp32 --port /dev/ttyUSB0 flash_id
...
could not open port '/dev/ttyUSB0': [Errno 16] Device or resource busy

Errno 16 is the kernel telling you the truth: the device file is already open somewhere. The board is fine, the cable is fine, the firmware is fine — the port is simply taken. Serial ports are exclusive by design: one holder at a time. The fix is always the same workflow — find the holder, release the port, flash. This is the checklist I run, in order.

Scope first. This covers your own hardware and hardware you have permission to work on. No scope, no probing — that rule applies to benches, not just networks.

1. The holder is usually you

Before blaming the system, check the obvious: a serial monitor in another terminal, a second esptool process, an Arduino IDE serial monitor, a PlatformIO device monitor, an arduino-cli monitor you forgot to close. Any process with the device open blocks everyone else. This is the most common cause and the most embarrassing one — find the process first:

$ fuser /dev/ttyUSB0
/dev/ttyUSB0:          4213
$ ps -p 4213 -o pid,comm,args
  PID COMMAND ARGS
 4213 python   python -m serial.tools.miniterm /dev/ttyUSB0 115200

Miniterm still running in a background terminal — close it and retry. lsof gives the same answer with more detail:

$ lsof /dev/ttyUSB0
COMMAND   PID USER   FD   TYPE DEVICE SIZE/OFF NODE NAME
python   4213 user    4u   CHR  188,0      0t0 1162 /dev/ttyUSB0

2. The holder is your browser

Chrome's Web Serial API keeps the port open as long as the tab lives. If you used esptool-web, Wokwi, or any browser-based flasher recently, the grant may still hold /dev/ttyUSB0 even though nothing looks "open". There is no visible terminal to kill — close the tab, or kill the browser, and the port comes back. This one burns people repeatedly precisely because the holder is invisible from the terminal.

3. The holder is your OS (Linux edition)

On Linux, two services compete with you for every USB serial device. The first is ModemManager: it probes newly attached serial devices to detect modems. That probe briefly opens the port — and sometimes wedges it. Check what it thinks about your board:

$ mmcli -L
    /org/freedesktop/ModemManager1/Modem/0 (ttyUSB0) [probing]

If ModemManager is holding the port, sudo mmcli -r resets it. For a permanent fix on a bench machine you will never use as a dial-up modem, mask the service so it stops probing entirely:

$ sudo systemctl mask ModemManager
$ sudo systemctl stop ModemManager

The second is brltty — the Braille display service, which claims USB serial devices it believes are Braille terminals. That includes many ESP32 dev boards. If the device misbehaves on a fresh plug, look at the kernel log:

$ dmesg | tail -5
[  123.4] usb 1-2: Product: CP2102 USB to UART Bridge Controller
[  123.5] brltty[612]: USB: device claimed by brltty

Fix: sudo apt purge brltty if you do not use a Braille display, or exclude the board's VID:PID in brltty.conf.

4. Permissions are not "busy" — but they look like it

A permission error is a different errno (Errno 13), but a port owned by root:dialout with your user missing from the group fails before the busy question even arises — and it reads just as opaque. Rule it out:

$ ls -l /dev/ttyUSB0
crw-rw---- 1 root dialout 188, 0 Oct 22 10:15 /dev/ttyUSB0
$ groups | grep -o dialout
dialout

No dialout in the output? Add yourself and log out and back in:

$ sudo usermod -aG dialout $USER

Until then, every denial will look like a dead board.

5. The five-minute checklist

Ordered, because order matters:

  1. Close every serial monitor, second esptool, and browser tab with a Web Serial grant.
  2. fuser /dev/ttyUSB0 (or lsof /dev/ttyUSB0) — kill the holder if you own it.
  3. Unplug, wait two seconds, replug. Then dmesg | tail to confirm the device re-enumerated as the same node — it may come back as ttyUSB1.
  4. Check ls -l and your dialout membership.
  5. If it is still busy on a fresh plug: ModemManager probing or brltty. Mask or purge as appropriate.

A smoke test that the port is genuinely free before relaunching esptool:

$ python3 -c "import serial; s = serial.Serial('/dev/ttyUSB0', 115200, timeout=1); s.close(); print('port free')"
port free

Closing

"Device or resource busy" is never the board and never the firmware. It is always a lock held by something else: your own monitor, your browser, or your distribution's serial-hungry services. Work the list top to bottom and the port comes back — no reboot, no new cable, no sacrifice.
