Status codes as an oracle

Servers answer every question you ask them — the trick is asking the right pairs of questions and reading what changes between the answers. A status code comparison is the cheapest oracle in my workflow: same endpoint, different conditions, and I watch which responses diverge. Divergences are threads. Identical answers are dead ends.

Scope first. Everything below assumes written authorization for the target. No scope, no recon — that rule is non-negotiable in my workflow.

1. The three-request comparison

The base pattern never changes. For any candidate endpoint I fire three manual requests, one at a time, and keep all three full responses:

$ curl -si https://target.example.com/api/profile > req-unauth.txt
$ curl -si https://target.example.com/api/profile \
    -H "Cookie: session=OWNSESSION" > req-auth.txt
$ curl -si "https://target.example.com/api/profile?id=0000" \
    -H "Cookie: session=OWNSESSION" > req-mutated.txt

The -i flag matters: status line and headers are part of the signal, not just the body. I only ever test with my own session and my own data — the oracle works the same whether the parameters point at real records or at values I control.

2. Read the matrix, don't chase one code

A single status code tells you almost nothing. The matrix tells you everything. I lay the three answers side by side:

$ for f in req-unauth.txt req-auth.txt req-mutated.txt; do
    echo -n "$f : "
    head -1 "$f"
  done
req-unauth.txt : HTTP/2 401
req-auth.txt   : HTTP/2 200
req-mutated.txt: HTTP/2 403

This shape — 401 → 200 → 403 — is informative: the endpoint checks authentication first, then applies an ownership rule that rejects my mutated parameter. Each layer revealed itself because I changed exactly one variable at a time. Now contrast it with the boring shape:

req-unauth.txt : HTTP/2 404
req-auth.txt   : HTTP/2 404
req-mutated.txt: HTTP/2 404

Three identical answers, including the body, means this input is a dead end — the server treats every variant the same way. I log it as "no divergence" in my dated notes and move on instead of sinking an afternoon into it.

3. The oracle lives beyond the number

Status codes are the headline, but the body and headers carry the rest. Two requests can both return 200 and still diverge — one returns a full object, the other an empty one. I diff the saved responses:

$ diff req-auth.txt req-mutated.txt
< {"id":"self","email":"me@example.com","role":"member"}
> {"error":"not_found"}

I also watch Content-Length, Set-Cookie, and any custom headers like X-Request-Id — a response that is 200 bytes longer than its twin is a divergence, even when both say 200. Timing counts too, but I treat timing as a weak signal: network jitter makes it noisy, so I only trust it when a pattern repeats across many manual probes.

4. When the oracle goes quiet

Sometimes the application normalizes everything: every bad input returns the same generic error page with the same code, because a global handler catches it first. That is not a failure — it is information about the defense layers. When all responses converge, the oracle is telling me the endpoint is uniformly gated, and I stop pulling that thread. Other days a WAF in front of the app answers before the app does, and the codes I see are the WAF's, not the backend's. I note which layer is talking before I draw conclusions.

What this gives you

The discipline is what makes this work at a human pace: one request, read the response, change one variable, read again. No scanner needed, no rate limits burned, no collateral noise. Most of my interesting threads started as a single line in a comparison table that didn't match its neighbors — a 403 where I expected a 404, a body that shrank instead of growing. The oracle never hands you a finding. It just tells you, reliably, where to look next.
